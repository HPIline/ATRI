## 软件栈（软件/atri）

“大脑—小脑”双层架构 + JSON 任务卡 + FSM + 五项技能 + **脚本动作库/步态生成**（已弃用 VLA）。
核心代码 **仅依赖 Python 3.14+ 标准库**，无硬件、无 GPU 也能跑通全流程。

已新增：
- `atri/perception/`：视觉感知接口 + Mock + OpenCV 实现（人脸/二维码/球）
- `atri/voice/`：离线关键词识别接口 + TTS（Mock / macOS say）
- `atri/qrgen.py`：二维码 JSON 指令生成器
- `action_library/`：动作库 JSON 规范 + 示例 + 校验/回放

```bash
cd 软件/atri

# 编译检查
python3 -m compileall -q atri run_demo.py && echo "compile OK"

# 单元测试（当前 334 项）
python3 -m unittest discover -s tests

# 无硬件闭环演示（五项任务卡；--fast 跳过 sleep 用于快速自检）
python3 run_demo.py --fast
```

### 审计核对了什么

- 22 自由度关节拓扑在**六处**交叉一致：`atri/config.py`、`design/robot_model.json`、
  两个 URDF、`webots/worlds/atri_22dof.wbt`、Webots 的两份 `joint_mapping`
- URDF 与世界文件可由生成器**字节级重现**
- 主包顶层第三方导入 **0 条**
- 工作树与提交历史中**无密钥**
- 当时 CI 在有提交时全绿

### 修复的严重问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | 技能失败仍上报 `status=ok` | 感知没看见球也照踢，上层无法得知失败 |
| 2 | `kick` / `dance` 的底层动作被下发两次 | 真机上重复执行同一动作 |
| 3 | 步数无上界，`timeout_s` 是死参数 | 任务可无限跑，声明的超时不起作用 |
| 4 | Webots 零绑定判"通过" | 电机名写错也报联调成功，实机不动 |
| 5 | `NaN` 被钳成限位上限 | 膝关节请求 `NaN` → 90°，等于把损坏输入驱动到满行程 |

### 复审后追加修复

- **超时预算基准**：技能循环原先在 `execute()` 内才取 deadline，比 FSM 定时器晚了整个
  `enter()`（含首次 `home()` 写 22 路总线）。`enter()` 耗时 ≥2 ms 时超时后仍会多跑一个技能
- **Webots 绑定判据改三层**：映射覆盖度（键集合必须恰好是 22 个合法关节名）+ 绑定完整性 +
  实际行程。此前三类假阳性都能判成"联调通过"——映射被截断（只写 1 个关节）、
  ATRI 侧键名写错（`head_pitchh` 让两个计数相互抵消，22/22 通过但该关节整轮未被驱动）、
  以及 `--velocity 0`（电机锁死、行程全 0）
- **`found` 只接受 bool**：此前 `found='False'`（非空字符串在 Python 里为真）仍判命中并真的踢球
- **`UnicodeDecodeError`**：它是 `ValueError` 子类，既不是 `OSError` 也不是 `JSONDecodeError`，
  此前在 4 条外部文件加载路径裸抛 traceback
- **`KickSkill` 缺测距**不再用硬编码 12 cm 兜底，改为观测 → 任务卡参数 → 判失败
- **设计数据口径**：减重路径的 `ankle_pct` 仍是废弃的 1.47 峰值口径，读起来像"减重即达标"；
  拆成连续额定 / 峰值双列后，按主判据 A=125–135%、B=110–120%、C=150%，**三条路径均未达标**。
  接口需求的电池容量改由 `power_budget()` 派生（≥4.53 Ah），删除硬编码 `≥2200 mAh`；
  标注 0.98 N·m 属 12 V 变体推断值、待实测，并给出 7.4 V 下限情形（踝约 333%）
- **测试空洞**：`test_available_false_without_cv2` 的断言 `assertIsInstance(..., bool)` 恒真；
  二维码的 kick / carry / grasp / release 四个合法动作零覆盖。两者都已补真实断言

### Python 版本策略

本项目**只支持 Python 3.14**，不再维护 3.9 / 3.11 / 3.12 兼容矩阵。

## ✅ 已决策：新架构 v3（2026-09-11）

**原"路线分歧"已收敛。** 处置办法：把整机尺寸对齐到量产参考机
（幻尔 TonyPi Pro，373 mm / 1.8 kg / 20 DOF），把模型质量从"结构占位预算"改成**真实分布**，
再于 v3 **把数据口径切到协作者 CAD 实装测量**（提交 6d4b077）。
完整参数见 **`design/handoff/新架构参数总表.md`**。

| 项 | v1（早期） | **v3（现行，CAD 实装口径）** |
|---|---|---|
| 身高 × 宽 × 厚 | 475 × 190 × 123 mm | **418 × 223 × 129 mm（CAD 实装）**；基元口径 372.8 mm |
| 整机质量 | 2263 g（实口径） | **3437 g**（结构件按 CAD 实算 1790 g） |
| link 质量口径 | 结构占位 1650 g，**不含舵机/电子件** | **结构 + 舵机 + 电子件 + 线束**（URDF 可直接做刚体动力学） |
| 最大关节需求 | trunk_roll 1.29 / 腿 1.11 N·m | **trunk_roll 2.092 / 踝 1.630 N·m** |
| 扭矩判据 | "额定 1.0 N·m"（当时无出处） | **连续额定 0.98 N·m（主判据，官方额定负载 10 kg·cm @12V）；峰值 1.47 N·m（堵转 × 50%）** |
| 结论 | 115% 额定，余量耗尽 | **踝 167% / 腰 214% ❌（占连续额定）**，必须执行减重路径 A/B/C |

**已修正的两个认识错误：**

1. **"结构减重数学上堵死"是错的。** 同尺寸下你们的结构件（v1 口径 552 g）比参考机放大到同尺寸还轻 15%
   —— 没有浪费。多出的质量里 220 g 是赛题要求的额外 4 个自由度，235 g 是原来更高的机身。
   （v3 切到 CAD 实装后结构件为 1790 g，上述定性结论不变，但绝对质量已按实算。）
2. **"余量耗尽"早期被归因于一个没有出处的额定值。** 该额定值现在有官方出处（0.98 N·m），
   但按 v3 实装质量，腿部关节确实**超连续额定**（踝 167%），所以"余量耗尽"在现行口径下**重新成立**。

**仍未消除的唯一硬不确定项**：STS3215 的真实连续扭矩与温升。
→ **建议动作：买 1 只 12V 版实测（约 90 元）**，这比换构型、换材料、买整机都便宜。

## 与外部部件库的协作

本项目缺少工业制品的世界知识（舵机孔位、轴承规格、走线工艺等），
这部分由外部部件库（Gemini 网页版）补充，协作方式：

```
Gemini  →  真实元件参数（型号/尺寸/质量/协议/工艺坑）
              ↓  人肉录入 design/components.json + design/cad/standards.py
本项目  →  check_fit.py 校验（装得下吗？重量对吗？力矩还够吗？）
              ↓
          反馈问题给对方，进入下一轮
```

**分工原则**：对方提供参数，本项目负责**一切需要与模型对照的判断**
（对方看不到模型，此类判断必错）。

已完成 3 轮，交接包见 `design/handoff/`。
