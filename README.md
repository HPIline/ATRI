## 软件栈（软件/atri）

“大脑—小脑”双层架构 + JSON 任务卡 + FSM + 五项技能 + **脚本动作库/步态生成**（已弃用 VLA）。
核心代码 **仅依赖 Python 3.9+ 标准库**，无硬件、无 GPU 也能跑通全流程。

已新增：
- `atri/perception/`：视觉感知接口 + Mock + OpenCV 实现（人脸/二维码/球）
- `atri/voice/`：离线关键词识别接口 + TTS（Mock / macOS say）
- `atri/qrgen.py`：二维码 JSON 指令生成器
- `action_library/`：动作库 JSON 规范 + 示例 + 校验/回放

```bash
cd 软件/atri

# 编译检查
python3 -m compileall -q atri run_demo.py && echo "compile OK"

# 单元测试（当前 168 项）
python3 -m unittest discover -s tests

# 无硬件闭环演示（五项任务卡；--fast 跳过 sleep 用于快速自检）
python3 run_demo.py --fast
```

## ⚠️ 路线分歧（待决策）

**这是当前最重要的问题，横在所有后续工作之前。**

用真实 CAD 零件 + 真实元件参数做的整机质量核算：

| 项目 | 质量 |
|---|---|
| 打印结构件（14 关节模块 + 8 连杆 + 2 足 + 4 转接） | 553 g |
| 舵机 22 × STS3215 | **1210 g** |
| 电子件 | 351 g |
| 线束 + 紧固件 | 150 g |
| **合计** | **2264 g** |
| 原设计预算 | 1650 g |
| **超出** | **+614 g（+37.2%）** |

**根因**：原质量预算制定时**未计入 22 颗舵机**（占整机 53%），
也未计入真实结构件。这是设计初期的口径问题，不是执行问题。

**连带影响**：关节力矩需求按总重等比放大 **×1.37**

| 关节 | 原需求 | 放大后 | STS3215 额定 |
|---|---|---|---|
| `trunk_roll` | 1.29 | **1.78 N·m** | 1.0 N·m |
| 腿部关节 | 0.84 | **1.15 N·m** | 1.0 N·m |

舵机额定 1.0 N·m 的工作余量将非常紧张（堵转 3.0 N·m 不能当连续扭矩用）。

### 三条出路的核算结果

| 方案 | 核算 | 结论 |
|---|---|---|
| **A. 结构减重** | 要回到额定以内需减重 **299 g**，但结构件总共只有 552 g | ❌ **数学上堵死** |
| **B. 换更强舵机** | 7 关节换 SM45BL：+1400 元、+350 g，腿需求落到 89% 额定 | ⚠️ 可行但**总价 4856 元，超预算 35%** |
| **C. 降低动态系数** | 慢速步态 2.0→1.4，腿需求降到 81% 额定 | ⭐ **零硬件成本**，但需核对赛题是否计速度 |

**成本与工时的完整核算见 `design/handoff/成本估算.md`**，摘要：

- 整机成本 **2788–3456 元**（自备打印机，只算耗材）→ **在 3600 预算内**
- 打印工时 **38–75 小时**（55% Gyroid 填充偏慢档），建议按 60–75 h 排产
- 最大零件 110×60×22 mm，宿舍级打印机（220×220×250）**无需分件**

### ⚠️ 但这个"115% 额定"的结论本身有不确定性

| 不确定项 | 说明 |
|---|---|
| 舵机额定扭矩 1.0 N·m | 来源标注"约"，厂商常只标堵转值，**额定缺乏权威出处** |
| 动态系数 2.0 | 工程估算，非实测 |
| 总重 2263 g | 由 CAD 体积 + 元件标称质量推算，**未实物称重** |

**所以正确结论不是"设计失败"，而是"余量已耗尽，必须实测"。**

**建议的下一步**（按性价比）：
1. **买 1 颗 STS3215 实测堵转/额定/温升**（90 元）—— 消除最大不确定性
2. **核对赛题评分细则**：行走速度是否计分 → 决定方案 C
3. **问部件库**：同尺寸（45.2×24.7×35）是否有更高额定扭矩型号
4. 以上都排除后，才考虑减自由度

**未决策前，不建议继续深化零件设计** —— 舵机型号与零件尺寸都取决于此。

## 与外部部件库的协作

本项目缺少工业制品的世界知识（舵机孔位、轴承规格、走线工艺等），
这部分由外部部件库（Gemini 网页版）补充，协作方式：

```
Gemini  →  真实元件参数（型号/尺寸/质量/协议/工艺坑）
              ↓  人肉录入 design/components.json + design/cad/standards.py
本项目  →  check_fit.py 校验（装得下吗？重量对吗？力矩还够吗？）
              ↓
          反馈问题给对方，进入下一轮
```

**分工原则**：对方提供参数，本项目负责**一切需要与模型对照的判断**
（对方看不到模型，此类判断必错）。

已完成 3 轮，交接包见 `design/handoff/`。
