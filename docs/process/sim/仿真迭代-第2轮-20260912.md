## 1. Webots 接触点探针：为什么不可用

先纠正一个 API 事实（读 `C:\Program Files\Webots\lib\controller\python\controller\*.py` 得到）：
`getSelf()` / `getFromId()` / `getContactPoints()` 都在 **`Supervisor`** 类上，`Robot` 没有。
用 `Robot()` 会在第一行抛 `AttributeError`——表现为"控制器没写出任何结果"，很容易误判成世界坏了。

于是做三组实测（临时工程 `_sync/wbprobe/`，未改仓库）：

| 世界 | 结果 |
|---|---|
| 零阻尼世界（第 1 轮已修） | ✅ 正常：5/5 任务、18/22 有行程 |
| `supervisor TRUE`，`selfCollision` 默认 FALSE | 控制器正常跑，`getContactPoints` 可调用，但**恒为 0 个接触点**（自接触不产生） |
| `supervisor TRUE` + `selfCollision TRUE` | ❌ **仿真卡死在第一个 `robot.step()`**：控制器心跳停在 step 3/15，40 秒后 Webots 进程仍在运行但毫无推进（不是 Python 异常——异常会被探针的兜底写出来；也不是正常结束） |

**为什么**：世界每个 link 只有一个盒子 `boundingObject`，而这些盒子在零位就大面积互相穿透
（姿态扫掠的基线统计：253 对 link 里 **163 对相交**，合计 6.9×10⁶ mm³）。
打开自碰撞 = 要求求解器把深度穿模的盒子推开 → 物理步死锁。

**结论**：想用接触点做动态碰撞验证，前提是**碰撞几何换成零件级、彼此不重叠的网格**
（把每件 CAD 的碰撞体导出成 mesh，替掉"一个 link 一个盒子"）。那是另一个工程量，
不是调参数能解决的。**所以：动态碰撞判据继续用 CAD 姿态扫掠；Webots 负责验证运动/指令链路**
（这一条在第 1 轮已经修好并复验）。

## 2. 限位收紧：听起来合理，实测无效

### 2.1 离线筛查（只筛"触发姿态是否还够得着"）——**会骗人**

| 情景 | 剩余事件 | 消掉 | 剩余 link 对 |
|---|---|---|---|
| 基线 | 632 | — | 21 |
| S1（肩滚 ±35、肘 -70…0、膝 0…75） | 452 | 180 | 11 |
| S2（S1 + 髋偏航 ±20 + 躯干滚 ±6） | 400 | 232 | 10 |
| S3（把触发过碰撞的 22 个关节全收到"任务需求 + 余量"） | 222 | 410 | 8 |

### 2.2 真跑 S3（改限位后**重新采样**）——**事件更多了**

```
python _sync/cad.py _sync/sweep_events.py verify S3
→ 116 姿态，719 个事件（基线 632），16 对 link
```

| | 基线限位 | 收紧到 S3 |
|---|---|---|
| 事件总数 | 632 | **719** |
| 事件 / 姿态 | 5.4 | **6.2** |
| 最大侵入 | 66 519 mm³ | 25 895 mm³（确实变小） |
| 涉及 link 对 | 21 | 16 |

**为什么筛查会骗人**：采样器是在**给定的限位盒内**取样的（单关节 3 档 + 50 组 LHS）。
把盒子收紧，采样就挤进收紧后的空间，而碰撞区本来就在里面 —— 事件的触发姿态根本不在
被切掉的那部分空间里，切掉它们自然没用。

### 2.3 单关节边际贡献（各自收紧，其余不动）

没有哪个关节能消掉 **>18%** 的事件：`hip_yaw` 17.9%、`shoulder_roll` 15–16%、
`trunk_roll` 13.0%、`elbow` 11.7–11.9%、`gripper` 9–11%…… 22 个关节每个都在 6–18% 之间。

**结论**：**碰撞是几何问题，不是行程问题。** 收紧限位只能把最坏侵入压小（66.5k → 25.9k mm³）
并砍掉个别极端对（比如两腿交叉），**不能消除自碰撞**；比赛要的是"任何下发姿态都不打架"，
靠限位做不到。限位最多当兜底，真正的解法是改机构包络 / 改零位姿态 / 控制器加 keep-out。

## 3. link 级 → 零件级：体积高估 ~10 倍，但碰撞是真的

用 `assembly.build_assembly(Kin(urdf, pose_deg=...), placements)`（同一套 86 件装配 + 配合判据）
把三个具体姿态查成零件级清单：

| 姿态 | link 级声称 | 零件级实测 |
|---|---|---|
| **扫掠最大事件**（肩滚 87°、肘 -76°） | `right_forearm ↔ torso_upper` **66 519 mm³** ❌ | 该对降到 ⚠️（`torso_frame ↔ 上臂管` 2747 mm³、`torso_frame ↔ 肘笼` 4057 mm³）；**新查出 ❌ `肘舵机 ↔ 夹爪舵机` 6369 mm³、❌ `前臂管 ↔ 肘舵机` 3657 mm³** |
| **次数最多**（71 次，肘 -111°、肩俯 -87°） | `left_forearm ↔ left_hip_yaw_link` ❌ | **❌ `肩俯舵机 ↔ 肘舵机` 10 080 mm³（24.4%）**；⚠️ `骨盆框 ↔ 左夹爪舵机` 3834、`左髋滚舵机 ↔ 左夹爪舵机` 3322 |
| **零位 + trunk_roll=10°** | `gripper ↔ hip_yaw/roll` ❌ | **❌ `右髋俯舵机 ↔ 右夹爪舵机` 7644 mm³（18.5%）**、**❌ `右髋偏航舵机 ↔ 右夹爪舵机` 5063 mm³**、**❌ `夹爪爪片 ↔ 右髋俯舵机` 1680 mm³（45.7% 重合）**、**❌ `髋偏航簇臂 ↔ 右夹爪舵机` 1306 mm³（43.8%）** |

要点：

- **link 级体积不可直接引用**：合并 collision 体把 link 内所有件并成一个形状，`forearm ↔ torso_upper`
  的 66.5k mm³ 在零件级只有几百~几千 mm³（同一区域内各零件错开）。**要用体积做决策，必须看零件级。**
- **但"会不会撞"是可信的**：三个姿态在零件级都确实出现了 ❌ 对，包括最扎眼的"零位 + 躯干侧倾 10° → 夹爪插进髋舵机"。
- **零件级能看见 link 级看不见的**：`肩俯舵机 ↔ 肘舵机`、`肘舵机 ↔ 夹爪舵机` —— 同一条手臂内部
  两个舵机互撞，link 级把整条手臂并成一个形状时完全查不出来。

## 4. 已验证的迭代：改 home 姿态消掉"手插髋"整族

`design/cad/assembly.py:43` 里本来就有一个**展示姿态** `DISPLAY_POSE_DEG`
（肩俯 -40°、肘 -55°、夹爪 20°、头俯 8°）——就是"手抬到身前"。

零件级实测（86 件装配 + 配合判据）：

| 姿态 | ❌ 对 | 总干涉 | ⚠️ 对 |
|---|---|---|---|
| 零位 + `trunk_roll=10°`（现状 home = 手臂下垂） | **4** | 180 871 mm³ | 118 |
| 展示姿态 + `trunk_roll=10°` | **2** | **148 363 mm³** | 99 |
| 展示姿态，`trunk_roll=0` | **2** | 147 883 mm³ | 98 |

- **"夹爪/簇臂 ↔ 髋舵机"那一族 ❌ 全部消失**（4 → 2），总干涉降 18%。
- 剩下的 2 个 ❌ 与姿态无关，是**静态就存在**的：`头俯舵机 ↔ 相机模组` 5241 mm³（24.2%）、
  `前臂管 ↔ 肘舵机` 4209 mm³（35.6%）——后者随肘折叠变大（伸直 2372 → 折 -76° 3657 → 折 -55° 4209）。
- 代价：肩俯 -40° 是"抬臂到身前"，**会改变站立/迎宾的外观与重心**（README 的口径是手在身侧）。
  这是设计取舍，不是纯技术问题。

**要落地需要改两处（有测试对账，不能只改一处）**：`software/atri/atri/config.py` 的 `rest_deg`
与 `design/robot_model.json` 的 `rest_deg`（现在两边都是「肘 -10、其余 0」）。
