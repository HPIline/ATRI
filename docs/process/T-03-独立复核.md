### 问题 2【中·事实性错误】gain 的等式写错（量纲不一致），出现在报告、工具 docstring 与随代码发布的 config

- **报告原文**（L149）：
  > gain 模型：gain = 物距 × tan(1°)，即相机像素当量/f；等效于针孔模型
- **`tools/carry_eval.py:18`**：
  > 闭环收敛与否由 **gain = 相机焦距(px) / 物距(cm)** 决定
- **`software/atri/config/carry.json:5`**：
  > ② 转 1° 身体时目标在画面里移动几厘米（→ step_gain，等于 相机焦距像素 / 物距cm …）
- **数值核对（12 cm 物距）**：`gain_cm_per_deg = 12×tan(1°) = 0.2095`；
  `f/物距 = 277.128/12 = 23.09`（单位是 px/cm，即像素当量）；`像素当量/f = 1/12 = 0.0833`（1/cm）。
  **三个数互不相等，量纲也不同**。
- 正确的三者关系：`gain[cm/°] = 物距·tan(1°)`；`像素当量 ppcm = f/物距 [px/cm]`；`画面横移[px/°] = f·tan(1°)`。
- **危害**：§6 给的死拍值公式 `1/(0.01745 × 物距cm)`（12cm≈4.8）是对的，但同一份材料里另有三处把它等同于
  `f/物距`（≈23）。按 `config/carry.json` 的回填指引算 `step_gain`，会差 **5 倍以上**——而这正是"实物到手照着调"的入口。
- **建议**：报告 L149 改为「gain = 物距 × tan(1°)；像素当量 ppcm = f / 物距（两者不是一回事）」；
  `carry_eval.py` 与 `config/carry.json` 同句照改。

### 问题 3【中·行为与文档不一致】「看见目标但没给横向偏移」时是 fail-open，与放置区通道的 fail-safe 不对称

- **实测**（`check_missing_x.py`，`.python` 零依赖即可复现）：

- **可达性**：仓库自带的两个后端在 `found=True` 时都会给 `x_cm`，所以**不是当前实跑路径上的 bug**；
  但外部注入观测（测评/任务卡 `observation`）、未来后端或字段改名都会踩到，且踩到时表现为"顺利夹取"。

### 问题 5【低·配置与文档不一致 + 告警不可见】`config/carry.json` 写了不存在的键 `give_up_cm`，且技能路径不打印 tuning 告警

- `software/atri/config/carry.json:4` 的 `_keys` 与 `:5` 的 `_calibration` 都写了 **`give_up_cm`**，
  但 `CARRY_DEFAULTS` 里没有这个键（对应的是 `grasp_tolerance_cm`，见 `carry.py:44`）。
- **实测**（命令 10 的 E 用例）：写 `{"give_up_cm": 1.0}` 进 tuning 文件 →
  `warnings=["未知键 'give_up_cm'（不在 carry 的可调项里）→ 忽略"]`、`overridden=[]`、行为完全不变。
- **而这条告警在现场看不到**：`carry.py:89` 调的是 `load_tuning("carry", CARRY_DEFAULTS)`（**没传 `warn`**；
  对比 `skills/kick.py:90` 传了 `warn=print`），告警只躺在 `Tuning.warnings` 里：
  成功路径塞进 `result["tuning_warnings"]`（L179）但**没有任何地方打印**；失败路径（L130-144）连这个键都没有。
  实测 C 用例：3 条告警（`deadband_cm` 负数、`step_gain` 字符串、`place_align` 字符串），技能 stdout **一条都没有**。
- **危害**：现场按 `_keys` 指引写 `give_up_cm` → 静默无效；按报告/日志所说的「只告警」，人却看不到告警。
- **建议**：`_keys`/`_calibration` 改成 `grasp_tolerance_cm`；`carry.py` 传 `warn=print`；失败结果也带 `tuning_warnings`。

### 问题 6【低·校验静默截断】int 型键给非整数 float 不告警，而是静默取整

- `tuning.py:122`：`int(number)`。实测（命令 10 的 C 用例）`{"max_iters": 2.5}` 被接受为 **2**，
  `overridden` 含 `max_iters`，**无 warning**；同文件里 `-3.0` / `"fast"` / `"maybe"` 都被正确拒绝并告警。
- 与 `tuning.py` docstring「类型不符…回落到默认值并记一条 `warnings`，**不静默**」有出入。
- **建议**：`want == "int"` 且 `not float(value).is_integer()` → 拒绝 + 告警。

### 问题 7【低·口径自定】「判据条件内 23/23」的"判据条件"在本仓没有 T-03 出处

### 问题 8【低·口径不一致】B 段相机参数与仓库自有的 `design/packages/perception_sim.json` 不同

## 5. 一句话结论

**这份成果能支撑**：「T-03 的控制律与放置区策略在**程序合成图像 + 一维几何**下真的跑得通（默认参数 11/20、
推荐参数 20/20）、失败会停手而不是硬夹、参数可在**不改编代码**的前提下从任务卡或 `config/carry.json` 标定回填、
且"多大偏差能纠"这张边界表可用**独立实现**复算到 0 处不一致」——
即**代码路径与调参依据**是可信的，报告里的数字（23/23、32/33、0.40/0.65/0.95 cm、11/20、20/20、3.4 cm、27 cm）
我一个不差地重跑出来了。

**这份成果不能支撑**：「抓取成功率 ≥80%」「实机能做到」「夹爪能夹住」「真实相机能检出」「放到位」之类的**实机能力**说法——
一次都没有测过。另外，**在下面三处我不认它的表述**：① §3「出画」列（4 行的"否"是错的，8cm 下 +5/+6cm 首帧中心确实在画面外）；
② §4/工具/配置里「gain 即 `f/物距`」这个等式（量纲与数值都不对，而它正是用来指导现场回填 `step_gain` 的）；
③ 收尾句「场景表 S-03 只规定了变化轴」（S-03 还有成功判据 8 轮，且与推荐的 `max_iters=15` 不一致，报告没提）。
另有 4 条较低severity 的配置/测试/口径问题（`give_up_cm` 键名错误且告警不可见、int 键静默截断、
"判据条件"无出处、任务卡优先级的对照测试是空断言）。**这些都不要替它找理由，交给主会话决定改法。**
