## 一、先把赛题原文和代码摆在一起看

赛题原文（第 3 轮 T6 复取）：**「② 二维码循迹：识别二维码并按指示路径行走。」**

代码里有什么：

| 环节 | 事实 |
|---|---|
| 生成端 `qrgen.py` | 只能生成**单条指令** `{"action":"walk","steps":3}` |
| 执行端 `skills/qr.py` | 单动作分发：walk / turn / dance |
| 识别端 `detect_qr` | `cv2.QRCodeDetector().detectAndDecode()` 单次裸调用 |
| 小脑层 `walk()` | 生成关节轨迹往下发，**不记录走到哪了** |
| 二维码测试 22 项 | **全部是校验参数**，没有一项用真二维码图验证"编码→解码" |

**结论两条**：赛题要的"路径"根本没有载体；而"按路径行走"里的"走到哪了"，当时的系统**答不上来**。

---

## 二、三个决策

**1. 路径 schema 带版本号，且**保留旧格式**。**

新格式 `{"schema":"atri.path.v1","path":[...]}`；旧的单指令格式继续可用，被解析成单段路径。
理由很实际：现场可能已经印好二维码了。而且旧格式解析后序列化回去**仍是旧格式**，
保证"同一个码，改前改后读出来一样"。

**2. 生成端与执行端共用同一套校验。**

原先 `qrgen.validate_params` 与技能层各写一份边界。本次把校验收进 `path_plan.validate_segment`，
成为**唯一实现**：生成得出但跑不通的二维码，不该被造出来。

> 这条规矩当天就抓到了我自己：评测脚本里我随手写了 `turn.deg = 180`，
> **被自己的校验器拦下**（上限 135°）。工具没白写。

**3. 三个解码器都实现，用数据选，而不是用直觉选。**

`opencv` 与 `aruco` 零下载、`wechat` 要 4 个模型文件。
直觉会选"零依赖"的那两个 —— 实测把这个直觉推翻了（下一节）。

---

## 三、实测推翻了直觉

27 个场景（尺寸 / 旋转 / 透视 / 模糊 / 亮度 / 噪声 / 组合）跑完：

| 解码器 | 判据子集成功率 | 全扫描 | 平均单帧 |
|---|---|---|---|
| `opencv`（自带） | 50.0% | 66.7% | **105.7 ms** |
| `aruco`（自带） | 66.7% | 59.3% | 54.0 ms |
| **`wechat`（需 1 MB 模型）** | **100%** | **88.9%** | **25.9 ms** |

三个反直觉之处：

1. **零下载的两个都达不到 90% 的判据要求**（50% / 66.7%），而"要下模型"的那个是 100%。
2. **最准的也是最快的**：`wechat` 25.9 ms，标准 `QRCodeDetector` 反而 105.7 ms —— 慢了 4 倍。
3. **成败几乎只取决于"码在画面里占多少像素"**：三种解码器在 45 px（名义 148 cm）时全部失败，
   而旋转 60°、亮度 ×0.4、噪声 σ=30 全都扛得住。也就是说 ——
   **现场要解决的是"印大一点 / 走近一点"，不是"换个算法"。**

这一节是本卷最想留下的东西：**"零依赖"是一个优点，但不是在这个指标上。**

---

## 四、两个"不做"和一个"必须说清"

**不做的第一件：不把标称值当实测。**

小脑层没有位移模型，所以 S-02 判据里的到位误差（≤50 mm）**测不了**。
我们建了 `atri/odometry.py` 做几何折算，让路径"算得出来"，但每条输出都带：

```
status: "nominal-uncalibrated"    caveat: "……未经实物标定，不可当作实测指标"
```

并且留好了实机标定的接口（`config/odometry.json`）。**先有接口，再谈数字。**

**不做的第二件：不改赛题没规定的格式。**

主办方未规定路径格式（T6 文档 Q3）。我们定义自己的 schema 并带版本号，
而不是假装这就是官方格式。将来对齐或并存都有落脚点。

**必须说清的：本报告的畸变是程序合成的。**

反光、运动模糊、打印质量、卡片卷边 —— 真实世界比合成图复杂得多。
报告里把这条写在"口径声明"一节，而不是藏在脚注。

## 五、本卷的三次自我订正

**1. 循环导入。** 把校验函数放在 `skills/base.py` 里，于是
`qrgen → path_plan → skills.base → skills/__init__ → skills.qr → odometry → path_plan` 绕成了环。
根因不是"import 顺序不对"，而是**函数放错了地方**：`as_finite_float` 这类东西与"技能"无关。
新建 `atri/validation.py` 作为中立位置，`skills/base.py` 原样再导出，既有写法全部不受影响。

**2. 替换误伤。** 我用脚本把 `_perspective` 里的 `warpAffine` 改成 `warpPerspective`，
结果把 `_rotate` 里同名的那行也改了 —— 两者用的是不同维度的矩阵（2×3 vs 3×3），
`_rotate` 当场就废了。**全局字符串替换在"同名不同义"的地方必须带上下文。**

**3. 自己的测试数据违反自己的约束**（第二节末尾那条）。留在这里，因为它正好证明校验器有效。

## 七、本卷沉淀的规矩（接卷 2 的 11 条）

12. **"零依赖"是优点，但不是在所有指标上都是优点。** 选型要让指标说话：
    自带解码器省了 1 MB 的模型，代价是判据条件下成功率 50%。这笔账不划算。
13. **先说清"测的是什么条件"。** 同一个解码器，判据子集 100%、全扫描 88.9%。
    只报一个数字，无论报哪个都是误导。
14. **标称值必须自带"我不是实测"的标记。** 不是写在文档某处，而是**写在数据里**
    （`status: nominal-uncalibrated`），这样它被引用到别处时也不会被误当成实测。
15. **同名不同义的替换要带上下文。** 同一次改动里 `_rotate` 与 `_perspective`
    各需要一个不同的 warp 函数，全局替换必然误伤其中一个。

## 八、与队友并行实现的合并：用实测判定，而不是用"谁写的"

推 T-02 时发现远端多了一条提交（`1cf0a8d`，队友），**同样在做 T-01～T-05 的补强**，
其中"路径序列"与"扫码"跟本卷正面重叠。两条线各自独立做到了同一件事，于是必须合并。

合并的判据不是"谁写的"，而是**谁真的能跑、谁的效果更好**。逐项实测如下。

### 8.1 转向：采纳队友的，且这次有数据

| 实现 | 实测行为 |
|---|---|
| 本卷原来的 `set_pose(hip_yaw=deg/3)` | 只发 **2 条静态指令**、**没有任何轨迹**；请求 90° 只拧 30°。机器人只是僵在一个拧住的角度上 —— **它根本不转** |
| 队友的 `cerebellum.turn(deg)` | 发 **120 帧踩步轨迹**（2.4 s）、240 条髋偏航指令，逐步叠加 |

**结论：队友的明显更好，采纳。** 这不是客气 —— 旧实现连"动"都没做到。

**同时测出一个双方都没说的事**：`turn(90)` 的髋偏航指令会被限位截到 **45°**
（`clamp_angle` 的 `hip_yaw` 上限就是 ±45）。也就是说转向**不能靠髋偏航完成**，
只能靠步态本身；而步态是否真的转过 90°，**没有位移/里程计就无法验证**。
这条已写进标称模型的说明里：`atri.odometry` 假设"指令的转角被实现了"，该假设**未标定**。

### 8.2 路径校验：改了队友的测试，理由写在测试里

队友的实现是**逐段校验**（第一段照走，第二段非法才失败）；本卷的实现是
**整条路径先校验**（一步都不走）。冲突。

判据：能静态判定的非法（未知动作、步数越界）为什么会出现？
- `qrgen` 生成时用的是**同一套严格校验** → 我们自己造的码**不可能**带这类段；
- 所以出现它，只可能是**码是外来的、或被损坏的**（解码出错但仍能解析成 JSON）。

**按一条已知损坏的路径走一半，比停在原地更糟**。所以选"先校验、一步不走"，
并把队友那条测试从"第一段照走"改成"一步都不走"，理由直接写在测试的 docstring 里
（不是悄悄改掉）。运行期才暴露的失败（小脑层报错）仍然逐段停下并报 `path[i]`。

### 8.3 合并时我自己引入的两个缺陷（都已被测试抓到）

1. **`odometry` 遇到 NaN 会裸抛 `ValueError`**。改成宽松校验后，未校验的参数会流到
   标称模型里，`int(nan)` 直接炸 —— 把整个技能结果毁掉。已改为"转不动按 0 计 + 在段上留 note"。
   标称模型是**事后推演**，它不该是那个抛异常的地方。
2. **预算检查抢在逐段校验前面**，报错变成"总步数超预算"，反而说不清是哪一段的问题。
   已把 `walk.steps` 写进报错文案。

两条都是"宽松化"带来的副作用 —— 再次印证：**放宽校验要连带动三处：校验、推演、报错文案。**

### 8.4 顺带确认：这次合并没有牺牲任何一方的能力

| 项 | 结果 |
|---|---|
| 队友的 `turn()` / `frame_source` / 五项补强 | 全部保留 |
| 本卷的路径 schema / 预算 / 标称位移 / 三解码器 / 评测工具 | 全部保留 |
| 队友对 T-01 口径的落地（改回「人脸识别」并区分两行语义） | 采纳（比本卷"待确认"的写法更准） |
| 全量测试 | **579 项**双环境全绿（零依赖环境自动跳过 44 项）、Webots 41 项无回归 |
