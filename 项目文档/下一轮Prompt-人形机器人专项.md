## 一、背景（执行者必读）

### 1.1 项目现状一句话

A.T.R.I.（Autonomous Tabletop Robotic Intelligence）是西安交大团队的**桌面级双足人形机器人**，报名中国国际大学生创新大赛（2026）陕西赛区**特色专项赛道·人形机器人专项·小人形组**。当前处于**方案设计阶段**：22 DOF 构型、软件栈（大脑 FSM + 小脑步态 + 感知/语音接口）、11 页 PPT、企划书均已完成，但**没有实物样机、没有仿真数据、没有实测证据**。

### 1.2 小人形组官方硬约束

| 项目 | 要求 | A.T.R.I. 设计值 |
|---|---|---|
| 结构 | 双足直立行走 + 自主脱线运行 | 满足 |
| 尺寸 | 高 ≤60cm，宽 ≤30cm，厚 ≤30cm | 37.3 × 18.7 × 10.6 cm |
| 电源 | 锂电池，≥7.4V，容量不限 | 11.1V 3S |
| 关节 | ≥18 个（每腿 ≥4，上肢+躯干 ≥10） | 22 DOF（腿10+臂8+躯2+头2） |
| 传感器 | IMU、摄像头、麦克风、扬声器 | 全部具备 |
| 赛道 | 2400×2400mm，含 5 个任务区域 | — |

五项比赛内容：① 人脸识别播报姓名 ② 二维码循迹 ③ 物品搬运 ④ 体育运动（踢球/投篮）⑤ 娱乐休闲（舞蹈/音乐/语音）

### 1.3 已提交/待提交材料

- 已交：企划书 + PPT（省级特色专项报名，截止 2026-08-28）
- **待交（关键）**：机器人实物展示视频（**≤3 分钟**）、技术方案说明书、**研发日志**、训练数据、**结构图纸**
- 材料上传硬死线：**9/13 18:00**（见 `项目文档/材料上传准备.md`）

### 1.4 评审修改意见的核心结论（`项目文档/修改意见.md`）

上轮评审给出的评分：文字自然度 7.5 / 结构完整度 8.5 / 专业性 8 / **技术可信度 5.5** / **创新性 5.5** / 竞争力 6。

三条最致命的批评：

1. **"方案书"而非"项目书"** —— 全文大量完成态表述（"小脑负责…""机器人识别…"），但进展表又说样机、仿真、五项任务全部"规划中"，前后口径撕裂。
2. **创新点不成立** —— 四条所谓创新（一机多任务 / 二维码下发指令 / 离线运行 / 版本控制）没有一条构成技术壁垒，都是"工程设计"或"研发管理"。
3. **"具身智能"名不副实** —— 实际是"感知 + 规则决策 + 动作执行"，动作大多是固定脚本，没有真正的视觉反馈闭环。

评审原话："**接下来只能靠真实成果提升**，文字包装空间已经不大。"

## 三、具体执行任务

### 任务 1（P0）：把"视觉伺服闭环"从设计变成可跑代码 + 数据

**问题**：目前 `atri/skills/` 里五项技能是"检测一次 → 调动作"的开环流程。评审明确要求："相机检测目标 → 计算误差 → 调整机器人位置 → **再检测** → 误差达阈值 → 执行抓取/踢球"。

**要做的事**：

1. 重构 `atri/skills/carry.py` 和 `atri/skills/kick.py`，加入**迭代式视觉伺服循环**：
   - 每轮：感知 → 算横向/距离/偏航误差 → 小脑执行一步微调 → 重新感知
   - 终止条件：误差 < 阈值，或迭代次数上限，或超时
   - 必须处理**不收敛**情况（振荡、目标丢失），并记录原因
2. 在 `atri/perception/mock.py` 中做一个**带噪声、带初始偏移的仿真目标**，让闭环有意义（当前 Mock 直接返回固定值，闭环跑起来是假的）。
3. 输出**闭环收敛数据**：每轮的误差序列，导出 CSV + 画收敛曲线（matplotlib 或纯文本图）。
4. 增加单元测试：闭环收敛、不收敛保护、超时保护。

**验收**：能跑出 `误差: 12.3cm → 7.1cm → 3.2cm → 0.9cm (达标)` 这样的真实日志，并有曲线图。

---

### 任务 2（P0）：Webots 仿真落地，产出第一份真实数据

**问题**：`webots/` 目前只有控制器骨架和 joint_mapping，从未跑过。评审说"五项任务协同尚停留在设计层面"。

**要做的事**：

1. 在 Webots 中搭建 22 DOF 机体（可先用内置 DARwin-OP / Nao 近似），完成 `joint_mapping.json` 对照校准。
2. 至少跑通三项任务的仿真：**二维码循迹**（有明确路径，最容易出数据）、**物品搬运**、**踢球**。
3. 采集并记录：
   - 双足连续行走距离与是否跌倒
   - 步态周期、步长、步高的**仿真实测值**（对比 `config/robot.json` 里 2.0cm / 1.2cm / 0.8s 的设计值）
   - IMU 姿态曲线（俯仰/横滚波动幅度）
4. 录制仿真演示视频（给 3 分钟展示视频做素材）。

**验收**：`技术方案.md` 的"阶段性技术指标"表里，"当前结果"列不再全是"未测试"，至少行走、平稳性两项有仿真数据 + 日期。

### 任务 3（P1）：确立一条能站住的"技术主线"

**问题**：现在的四条创新都不是创新。评审给的方向是：**把问题收敛到一个具体命题**——

> "小型双足机器人在有限算力和断网条件下，如何通过统一任务描述实现多任务自主执行？"

**要做的事**：

1. 围绕 `JSON 任务卡 + FSM + 技能库 + 视觉反馈 + 本地执行` 这条链，找出**真正的技术点**。候选方向（择一深挖，不要全要）：
   - **A. 任务描述的可组合性**：证明新增任务只需写 JSON + 一个技能模块，无需改框架。给出"新增第 6 项任务用了多少行代码 / 多少分钟"的量化证据。
   - **B. 闭环的鲁棒性**：证明视觉伺服在噪声、遮挡、弱光下仍收敛。给出成功率-干扰强度曲线。
   - **C. 低成本约束下的步态可行性**：22 DOF、2cm 步长、1.65kg 下，论证什么让步态稳定（ZMP 余量、踝关节取舍）。
2. 把选定的方向写成 **1 页技术说明**，放在企划书和 PPT 的最前面。
3. 同步更新 `项目文档/答辩Q&A.md` 的 Q2（"创新点到底是什么"），答案要从"系统集成 + 工程优化"升级为具体的技术主张。

**验收**：能对着评委用 30 秒说清楚"我在什么约束下解决了什么问题，证据是什么"。

### 任务 4（P1）：补结构图纸与 CAD

**问题**：评审原话——"22 DOF 现在只是纸上的数字。评委检录时看的是：**这个 2 DOF 躯干在哪里？图纸比文字更重要。**"

**要做的事**：

1. 出 **总装结构图**：三视图 + 关节编号图（22 个关节逐个标注），明确标出躯干 2 DOF 的位置。
2. 出 **连杆尺寸链**：大腿/小腿/上臂/前臂长度，验证臂长（单侧）≤30cm。
3. 若有可能，出 3D 打印件清单（哪些件、什么材料、预计克重）。
4. 统一修正一个已知硬伤：**踝关节自由度前后矛盾**（旧稿一处写"踝部两个"=每腿 6 DOF，另一处写"踝1"=每腿 5 DOF）。全仓库统一为 **髋3 + 膝1 + 踝1 = 5**。

**验收**：有一张能放进技术方案说明书、评委能看懂的结构图。

### 任务 5（P2）：统一全文口径

**问题**：完成态表述与实际进展不符，是最容易被抓的失分点。

**要做的事**：

1. 全仓库（企划书、PPT、技术方案、README）统一使用三词口径：**设计目标 / 当前状态 / 后续计划**。
2. 尚未实现的一律改为"设计为负责…""计划通过…""当前先在仿真中验证…"。
3. 删除评审点名要求删的两句：
   - "方案与研发记录同源"
   - "风险应对以先行验证和材料留痕为主线"
4. 所有尚未确定的硬件型号，要么给真实型号，要么明确写"在样机阶段根据扭矩/重量/供电需求确定"，**不允许一边写得像成熟产品一边全部"后续确定"**。

## 四、给执行者的约束与红线

1. **不许编造数据**。所有"当前结果"必须来自真实运行的代码或仿真，注明运行日期与环境。没有就说没有。
2. **不许用文字抬高项目**。评审已经明确：文字包装空间耗尽，只能靠真实成果。
3. **软件保持零第三方依赖**（核心栈仅 Python 3.9+ 标准库）。仿真/绘图脚本可单独依赖。
4. **改动前先 `git pull --rebase origin main`**，小步提交，**禁止 force push**。
5. 不要提交 `__pycache__/`、`.venv/`、`.DS_Store`、视频大文件。
