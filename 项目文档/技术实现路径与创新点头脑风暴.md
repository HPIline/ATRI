## 第二部分：技术实现路径（怎么真做出来）

### 2.1 步态：当前设计有一个根本性缺陷

看 `cerebellum.py:generate_gait()` 的实现——它用的是**两条腿各自独立的正弦波**：

```python
left_swing  = math.sin(phase)
right_swing = math.sin(phase + math.pi)   # 相差 180°
left_amp    = max(0.0, left_swing)        # 半波整流
```

问题在于：

1. **没有 ZMP（零力矩点）判据**。PPT 第 4 页写着"基于 ZMP 与倒立摆模型，毫秒级解算"，但代码里**没有任何 ZMP 计算**。这是文字与实现脱节最严重的地方。
2. **`max(0, sin)` 半波整流会产生速度突变**，在真实舵机上表现为抖动，在仿真里表现为失稳。
3. **没有质心（CoM）轨迹规划**。双足行走的本质是"控制质心落在支撑多边形内"，当前完全没有这个约束。
4. **躯干 pitch/roll 是随手加的正弦扰动**（`1.5*sin(phase)`、`1.0*sin(phase/2)`），不是平衡补偿。

**要做的**：
- 实现 **LIPM（线性倒立摆模型）**：`ẍ = ω²(x - p)`，其中 `ω = √(g/z_c)`
- 由期望 ZMP 轨迹**反解** CoM 轨迹（解析解，纯数学，无需机器学习）
- 用 **三次样条或摆线** 替代正弦做摆动腿轨迹，保证速度连续
- 加 **IMU 反馈**：实测姿态偏差 → 修正踝关节
- 输出 **ZMP 稳定裕度**数据（质心到支撑多边形边界的距离）——这就是能拿给评委看的量化证据

> 这是**纯算法工作，零硬件依赖，可以在仿真里完整验证**。也是把"PPT 上写的 ZMP"变成"代码里真的算了 ZMP"的关键。

### 2.2 视觉伺服：把开环变成真闭环

当前 `carry.py` / `kick.py` 都是"**感知一次 → 执行动作**"。

**要做的**：迭代闭环控制器

```
循环（最多 N 次 或 超时 T）：
    感知目标 → 计算误差 e = (Δx, Δy, Δθ)
    if |e| < 阈值: break
    执行一步微调（步长 ∝ e，做饱和限幅防振荡）
    记录本轮误差
返回：收敛序列 + 迭代次数 + 是否收敛
```

三个必须处理的工程问题：

1. **防振荡**：增益过大 → 来回摆动。需要让步长随误差衰减（如 `step = k*e` 且 `step ≤ max_step`）。
2. **目标丢失**：视觉短暂丢失目标时不能立刻放弃，要**搜索策略**（原地转头扫描 + 用上轮位置预测）。
3. **不收敛保护**：达到迭代上限就安全退出并上报，不能卡死。

**产出数据**：误差收敛曲线（这是最有说服力的一张图——它直接证明"机器人是根据视觉反馈调整自身状态，而不是执行固定脚本"）。

### 2.3 搬运的隐藏难点：负载对步态的影响

抓取一个物体后，**质心位置变了**。如果不重新规划步态，机器人会前倾或侧翻。

这是**真实工程取舍的好素材**：
- 物体 ≤100g、机器人 3.437kg（v3 CAD 实装）→ 负载比约 2.9%（减重到 2.2 kg 后约 4.5%）
- 抓取后 CoM 前移量可以估算，据此**调整躯干 pitch 补偿**
- 这个"会自适应调整"的细节，比空喊"具身智能"有力得多

### 2.4 离线语音：当前只有接口，要落地

`voice/` 目前只有 Mock 和 macOS `say`。需要在目标平台接真实引擎：
- **关键词识别**：Vosk（小模型中文约 40MB）或 sherpa-onnx，纯离线
- **TTS**：Windows 可用 SAPI / piper，macOS 用 `say`（已有）
- 注意：要满足"自主脱线运行"，**不能依赖云端 API**

### 2.5 仿真先行的路径

Webots 里可用的现成人形模型：**DARwin-OP**（20 DOF）、**Nao**（25 DOF）。都和我们 22 DOF 接近，可以先用它们把算法跑通，再迁移到自研机体。

`joint_mapping_nao.json` 已经建好了，说明这条路已经想过了。

## 第三部分：创新点 —— 什么能让评委眼前一亮

### 3.1 先说残酷的事实：常规"创新点"都不成立

以下这些，评委每年看几百份，**不构成任何区分度**：

| 常见写法 | 为什么不算创新 |
|---|---|
| "一台机器人完成五项任务" | 这是赛题规定，不是创新 |
| "二维码下发 JSON 指令" | 是工程技巧，且容易被认为"花招" |
| "全离线运行" | 比赛规则的硬性要求，做到了是应该的 |
| "成本低、可教学复用" | 是商业定位，不是技术壁垒 |
| "用了 ZMP / 逆运动学 / 深度学习" | 用现成方法是实现，不是创新 |

### 3.2 真正的创新机会：从"我做了什么"转向"我发现了什么问题"

评委记住的从来不是功能列表，而是**一个具体的技术洞察**。以下是几个我认为真正有区分度的方向：

---

#### 方向 A：把"任务描述"做成可组合的形式化规范 ⭐⭐⭐⭐⭐

**洞察**：市面小型双足机器人的软件都是"一个任务一个程序"，换场地/改规则就要重烧代码。我们能不能让**新增一项任务只需要写配置，不需要改框架**？

**技术主张**：
> 提出一套 **JSON 任务卡 + 技能注册表** 的组合式任务描述规范，把"任务做什么"与"机器人怎么做"彻底解耦。技能是原子能力，任务卡是能力的有序组合，感知/决策/执行通过统一上下文注入。

**怎么证明它是真的**：
- 现场演示：**用一个 20 行的 JSON 文件新增第 6 项赛题外的任务**，全程不改一行业务代码
- 量化：`新增任务的平均代码量从 XXX 行降到 YY 行`
- 这是**可当场验证**的，比任何形容词都强

**为什么有壁垒**：它要求框架设计得足够抽象（任务卡校验、技能上下文、参数注入、超时/异常统一处理）。做出来不难，但**做得干净**很难，而干净程度一眼能看出来。

---

#### 方向 B：把"闭环收敛"变成可测量的鲁棒性指标 ⭐⭐⭐⭐⭐

**洞察**：所有队伍都会说"我们做了视觉闭环"，但没人量化**闭环在什么条件下会失效**。

**技术主张**：
> 建立小型双足机器人在**桌面场景**下的视觉伺服收敛性评测方法：在受控扰动（光照变化、目标偏移、部分遮挡、地面摩擦差异）下测量收敛成功率与迭代次数，给出**失效边界**。

**怎么证明**：
- 横轴：扰动强度（如目标初始偏移 0→30cm、光照 100→800lux）
- 纵轴：收敛成功率
- 一条曲线，清晰说明"我们在什么范围内可靠"

**为什么有壁垒**：**主动暴露自己的能力边界，反而显得极其可信**。评委见过太多"我们的成功率达到 95%"，第一次见到"我们在 X 条件下会失败，因此设计了 Y 降级策略"的，会立刻记住。

---

#### 方向 C：低成本 + 欠驱动约束下的步态可行性论证 ⭐⭐⭐⭐

**洞察**：22 个 ~90 元的舵机 + 3D 打印结构，做双足行走是**逆天难度**。真实问题不是"我们的步态很优美"，而是"在这么差的硬件上，什么让步态勉强可行"。

**技术主张**：
> 论证在**低成本舵机（无扭矩反馈、有回程间隙）+ 简化踝关节（仅 1 DOF）**约束下，双足稳定行走的参数可行域。给出步长-周期-质心高度的稳定边界。

**怎么证明**：
- 步态参数扫描：步长 × 周期 → 稳定/失稳 相图
- 解释取舍：为什么踝关节只保留 pitch（重量/成本 vs 横滚补偿靠髋关节）

**为什么有壁垒**：这是**真正的工程诚实**，而且是只有真做过仿真/调过参数的人才写得出来的内容。

---

#### 方向 D：把"具身智能"落到一个具体机制上 ⭐⭐⭐⭐

**洞察**："具身智能"这个词太大会被追问。不如**用一个具体机制定义它**。

**技术主张**：
> 具身性体现在：**机器人的动作参数不来自固定脚本，而来自当前感知状态的实时计算**。同一个"抓取"技能，面对不同距离/角度的目标，产生不同的关节轨迹。

**怎么证明**：
- 同一个任务，改变目标初始位置 → 记录**实际下发的关节角序列不同**
- 对比实验：开环脚本 vs 闭环伺服，成功率差异

**为什么有壁垒**：它把"具身智能"从**名词**变成了**可观测的行为差异**。

---

### 3.3 我的推荐组合

**主创新点选 A（任务描述的形式化），辅创新点选 B（收敛性边界）。**

理由：
1. **两者都纯软件**，不需要等硬件，现在就能做出来
2. **都有可当场验证的证据**（一个 20 行 JSON，一条收敛曲线）
3. **互补**：A 证明"架构有思考"，B 证明"工程有深度"
4. 避开硬件短板：不需要先把机器人造出来才能讲创新

方向 C 作为**答辩时的加分回答**（被问到硬件取舍时抛出），方向 D 作为**"具身智能"这个词的护身符**。

## 第四部分：我们的计划 vs 应该有的样子

### 4.1 当前计划的薄弱环节

| 环节 | 现状 | 问题 |
|---|---|---|
| 阶段一 方案设计 | 已完成 | ✅ 无问题 |
| 阶段二 仿真与借机 | "进行中" | ⚠️ 实际未开始，无任何数据 |
| 阶段三 硬件自组 | "晋级后" | ⚠️ **最大风险**：人形专项没有机器人 |
| 阶段四 彩排拍摄 | "冲刺期" | 依赖阶段二、三 |

**核心风险：整个计划是"先交材料，等晋级，再做东西"。而人形机器人专项的评审，最想看到的就是"东西"。**

### 4.2 建议调整：把"零硬件的可验证成果"提到最前面

不需要等硬件，现在就能产出的**硬证据**：

| 可立即产出 | 形式 | 证明什么 |
|---|---|---|
| ZMP 步态 + 稳定性仿真 | 曲线 + 相图 | 步态不是随手写的正弦 |
| 视觉伺服收敛数据 | 收敛曲线 | 闭环是真的 |
| 扰动鲁棒性测试 | 成功率-扰动曲线 | 知道自己能力的边界 |
| 新增任务演示 | 20 行 JSON | 架构可扩展 |
| Webots 行走视频 | 视频 | 有动态证据 |

**这五样东西全部不需要实物样机，但能让材料从"方案书"变成"项目书"。**

### 4.3 硬件路线的现实建议

评审一定会问："**你们报名人形机器人项目，机器人在哪？**"

三条路，按推荐度排序：

1. **借**：校内实验室、其他队伍、往届学长。哪怕机型不同，标注"借用平台，用于验证算法"即可。**有真机视频 > 纯仿真 >> 只有 PPT**
2. **买二手/成品**：TonyPi Pro 一类的成品机可以作为验证平台
3. **自组**：约 1500-2800 元，但**周期最长、风险最高**（3D 打印 + 22 舵机装配 + 调试，不是短时间能完成的）

**建议：材料里明确写出"借用平台验证算法"这一步，并把借用机型的差异说明清楚。** 这比含糊其辞地写"晋级后自组"要可信得多。

## 附：一个诚实提醒

现在的软件栈 1488 行、51 项测试，架构是干净的，接口设计有想法。**它的问题不是"做得差"，而是"还没证明它能跑"。**

评委不会因为"代码写得好"给高分，但会因为"有数据、有边界、有可复现的证据"给高分。

**把已有的干净架构，变成有数字支撑的技术主张——这是性价比最高的一步。**
