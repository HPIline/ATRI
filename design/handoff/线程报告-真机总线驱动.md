## 3. 驱动实现要点（对照交付要求）

| 要求 | 实现 |
|---|---|
| 类名与构造参数 | `Sts3215Bus(ServoBus)`，`(port, baudrate=1_000_000, timeout_s=0.05, calibrations=None, serial_factory=None, ser=None, retries=2, goal_speed=0, goal_acc=0, verify=True)`；另给别名 `StsBus`（交接文档与 `run_bringup.py` 里用的就是这个名字） |
| 串口可注入 | `ser=`（现成对象）或 `serial_factory=`（可调用对象）；二者都不走 pyserial |
| pyserial 延迟导入 | 顶层只有 `import select/threading/time`；`import serial` 在 `open()` 内部，缺库时抛 `StsSerialUnavailable`，消息含**中文排查步骤 + 完整解释器路径的 pip 命令** |
| `sync_write` = 一条广播帧 | `make_sync_write_frame()` 组 `INST_SYNC_WRITE(0x83)`、ID=254；22 关节一帧 ≈ 74 字节 ≈ 0.6 ms（1 Mbps）。**不是**循环 `set_angle` |
| `scan()` | 0–253 逐个 PING，**默认每 ID 超时 2 ms**（253×50 ms = 12.7 s 等不起）；跳过 253/254 |
| `read_telemetry()` | 一次读 56…66 共 11 字节 + 69/70 电流；键名 `pos_deg/load_pct/voltage_v/temp_c/current_a/moving` **与 `MockServoBus` 完全一致**，另附 `speed_raw/current_raw/load_raw/position_raw/status` 诊断键 |
| `write_limits()` | 写 EEPROM 9/11（16 位小端）；先关扭矩 40=0 → 写 → 恢复原扭矩 → **回读校验**，不一致抛 `StsDeviceError` 并提示"寄存器 55 可能锁着" |
| `set_middle()` | 默认走真机制：读当前位置 → 关扭矩 → 写 31 号位置偏置 → 恢复扭矩 → 回读校验（见第 5 节冲突说明） |
| `relax_all()` | **广播**写 40=0，一帧让全总线松轴 |
| 读重试 + 校验和 | `_read_regs()` 重试 `retries+1` 次，坏帧丢弃并累加 `bus.bad_frames`，重试耗尽抛 `StsTimeoutError`，消息区分"全坏帧"与"全超时"并给出不同排查重点 |
| 角度边界钳制 | `_clamp_pulse()` 用 `config.pulse_limits()` 钳制，**任何情况都不把越界脉冲发给舵机**，并记 `last_errors` |

**一处设计取舍（已实测）**：`sync_write` 在**每条位置帧之后**会回读一次位置做闭环校验
（`verify=True` 默认开）。实测（内存假串口，假总线**永不回包**，所以每次都等满 50 ms 超时）：

```console
$ cd 软件/atri && ./.venv/bin/python - <<'PY'   # 实测片段
verify=False: 0.179 ms, 发出帧数=1
verify=True : 1186.076 ms, 发出帧数=23（1 位置帧 + 22 次回读）
1 Mbps 理论帧时间: 74 字节 × 10 bit / 1e6 = 0.740 ms
PY
```

即 **`verify=True` 的代价 = 22 次读往返**。假总线因不应答，每次都吃满 50 ms 超时，
所以得到 1186 ms；真机上舵机有应答（1 Mbps 下 8 字节回包 ≈ 0.1 ms），
实际是"22 × (往返 + 舵机响应)"，量级为**数毫秒**——但**仍会吃掉 20 ms 周期的一大块**。

**结论**：bring-up / 单关节调试保持默认 `verify=True`（"舵机没到位"是机械干涉的最早信号）；
**步态巡检与任何 20 ms 周期场景必须显式 `verify=False`**（或用 `sync_write` 之外的裸帧路径）。
真机上第一件事就是把 `verify=True/False` 的实际耗时各测一次。

## 4. 调试过程中真实踩到并修掉的坑（都已在测试里钉住）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | **读完清输入缓冲** | 假串口里每次读都超时 | `reset_input_buffer()` 必须在**写之前**清（半双工应答是写后才到，写完再清就把回包扔了）。改为 `_transaction()` 写前清 |
| 2 | **SYNC WRITE 行格式** | 写进去的脉冲和读出来差一格 | 飞特载荷是 `起始地址｜每舵机数据长度｜(ID,data…)×N`：**每行自带 ID，而"数据长度"只数数据字节、不含 ID**。修 `make_sync_write_frame` 并加"行长必须 = width+1"的断言 |
| 3 | **JOINTS 索引缓存** | 个别关节读到别的关节的角度 | `_joint_of_id` 原来缓存 ID→名映射；`load_calibration()` 会就地改 `JOINTS`，缓存就过期了。改成**每次现算**（22 项字典推导，开销可忽略） |
| 4 | **16 位寄存器只记低字节** | 2048 读回 0 | 2048 = 0x0800，低字节本来就是 0；假串口必须把 L/H 两字节都摆出来 |
| 5 | **测试里 reload 驱动模块** | 单独跑绿、一起跑红 | `importlib.reload()` 会重建模块里的异常类，测试顶部 import 的 `StsTimeoutError` 变"旧类"，后面所有 `assertRaises` 失配。改成**子进程**验证缺 pyserial 场景 |
| 6 | **假串口应帧死循环** | 测试挂死到超时 | 坏长度帧必须**丢掉一个字节**重找帧头，否则 `while True` 原地打转 |

坑 2 是**真机级 bug**：行错一格在真机上表现为"舵机乱转/不动"，而假串口只按协议解码、
不做容错，所以才能把它暴露出来。这也是坚持让测试**独立实现一遍组帧/解帧**（不复用驱动代码）的原因。

## 5. ⚠️ 与既有文档的一处冲突（已核验，请以 `PROTOCOL.md` 为准）

**冲突点**：交接文档 `design/handoff/给Grok-真机链路对接文档.md`（2.2 / 3.2 节）与
`cerebellum.set_middle` 的 docstring 都写"中位标定 = **40 号地址写 128**"；
本次任务书也把这条列为"关键协议事实"。

**核验结果**：`design/reference/sts3215/PROTOCOL.md` 3.2 节与
`design/reference/sts3215/STS3215_Register_Reference.md` **两份独立来源**都写明：

- **地址 40 = Torque Enable**（0 = 松轴，1 = 锁轴）
- **地址 31 = Position Offset**（位置偏置，2 字节，零位标定值）

把 `128` 写到 40 号，在协议上就是"扭矩使能 = 非 0"（等效开扭矩），
**不会**改变零位；而且 `set_middle` 的语义是"以当前位置为零位"，
真要实现就必须写 31 号（偏置 = 当前位置 − 2048）。
推测 "128" 来自飞特上位机工具里 0–255 的"中点"刻度（128 居中），
被误当成了"寄存器 40 写 128"。

**处理方式**（任务书要求"如有冲突以 PROTOCOL.md 为准并在报告中指出"，故此处双轨）：

- `set_middle(joint_id)` **默认走真机制**：读当前位置 → 关扭矩 → 写 31 → 恢复扭矩 → 回读校验。
- 保留字面兼容通路：`set_middle(joint_id, addr=ADDR_TORQUE_ENABLE)` 精确写出
  "40 号地址写 128"，并记一条 `last_errors` 警告说明它只开扭矩、不改零位。
- 两条路径都有单测（`test_set_middle_writes_offset_register`、
  `test_set_middle_negative_offset_is_twos_complement`、
  `test_set_middle_compat_path_writes_128_to_40`）。
- **现场建议**：先拿 1 只舵机试默认路径，用 `read_pulse()` 确认零位真的变了，再对 22 只批量做。
  这一条已在 `固件/README.md` 6.1 节写明。

**其余寄存器地址核对**：`PROTOCOL.md` 的 5 / 6 / 9 / 11 / 33 / 40 / 42 / 55 / 56 / 60 /
62 / 63 / 69 与本驱动常量**逐条一致**，未见其他冲突。

## 7. 已知未做项 / 没有硬件时尚未验证的行为

### 7.1 完全未经真机验证（**最重要**）

| # | 未验证项 | 风险 | 硬件到了怎么最先验 |
|---|---|---|---|
| 1 | **串口物理层**：1 Mbps 下 pyserial 的收发时序 | 高 | `--step scan`；扫不到就先降到 115200 试（需同步改舵机寄存器 6） |
| 2 | **半双工换向** | 高 | 普通 USB-TTL 靠 1 kΩ + RX 直连这一招在 1 Mbps 下**是否真的可行**（URT-1 自动换向则无此风险）；先单只舵机验 |
| 3 | **`reset_input_buffer()` 的时机** | 中 | 真串口上"写前清"会不会清掉上一个事务的迟到回包；若出现偶发超时，改为"只在空闲时清" |
| 4 | **写后回读的判据** | 中 | `tol_pulse=12`（≈1°）是拍的；真机上要看静止/运动中分别的抖动，可能要放宽 |
| 5 | **EEPROM 写入生效时间** | 中 | `reset()` 里沿用官方 SDK 的 20 ms 延时；真机若回读不一致，加长或改"关-开扭矩" |
| 6 | **零位偏置的符号约定** | 中 | `offset = 当前位置 − 2048` 是按"偏置为正 = 舵机零点往高位挪"推的；真机上必须用 1 只舵机验方向，反了就取反 |
| 7 | **限位寄存器与软件限位的关系** | 中 | 写进舵机的 9/11 是"软件限位外扩 3°"，真机上要确认它确实**比软件限位宽、比机械硬限位窄** |
| 8 | **电流寄存器 69 在 12 V 版是否有效** | 中 | 官方规格书称支持；驱动已做"读失败 → `current_a=None`"的降级，真机看 `last_errors` |
| 9 | **22 只并联总线的电气特性** | 高 | 反射/容性负载会让 1 Mbps 波形变差；这也是"单只先通、再逐只加"的原因 |
| 10 | **SYNC WRITE 在真舵机上的实际响应** | 高 | 假串口只按协议解码；真机上要确认 22 只确实同时动、且限速帧先生效 |
| 11 | **`scan()` 的 2 ms 超时够不够** | 中 | 漏扫就调到 5–10 ms（已在 docstring 写明） |
| 12 | **`verify=True` 在 20 ms 周期下的开销** | 中 | 22 次回读会吃掉数毫秒；步态巡检必须 `verify=False`，需实测确认 |
