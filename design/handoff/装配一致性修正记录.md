## 1. 根因（三条，都是系统性错误）

### 1.1 舵机占位体比 `orient()` 的约定差 90°（影响全部 22 个关节）

`assembly.servo_placeholder()` 按"输出轴沿 **+Z**"建模（Φ20 盘放在 ±Z），
而 `kit.orient()` 的约定是**局部 +Y → 输出轴、+Z → 母端**。
两者差 90° ⇒ 每个关节的舵机都横躺着，机体的 45.2 长边顶进相邻结构里
（这就是预览里"到处穿模、方向怪"的主因）。

### 1.2 `orient()` 本身不可靠（yaw 类方向对映射错误）

原实现用 `gp_Trsf.SetTransformation(gp_Ax3(from), gp_Ax3(to))`。
实测（标记块法）发现：当 `(shaft, parent)` 取到"轴与母端分属不同坐标轴"的某些组合时，
**局部 +Y 并没有走到 shaft 上**——例如 `shaft=-z, parent=+y` 时局部 +Y 落在世界 Y 上。
`hip_yaw` / `head_yaw` 正是这一组合（轴与母端同轴，代码用"取一个垂直方向当母端"的退化处理，
于是撞上这个 bug），所以 **yaw 关节的舵机整整歪 90°**。

**已重写为显式右手正交矩阵**，映射关系可逐条验证：

```
局部 +Y → shaft        局部 +Z → parent        局部 +X = shaft × parent
```

### 1.3 舵机包络的 35 与 24.7 用反 + 安装孔开在了错误的板

`skeleton.py` 里：

```python
L_S, W_S, H_S = S["body_mm"]      # 45.2 / 24.7 / 35.0
GAP = W_S + 0.5                   # 25.2 ← 两侧板净距，但沿轴厚度是 35.0
AXIS_DZ = servo_axis_offset_mm()  # 6.5  ← 轴线其实在宽度方向居中
Z_TOP = H_S/2 - AXIS_DZ           # +11.0 ← 应为 +12.35
Z_BOT = -H_S/2 - AXIS_DZ          # −24.0 ← 应为 −12.35
```

- 官方与实测一致：**35.0 是沿输出轴的厚度**，垂直轴截面是 45.2 × 24.7；
- 且**轴心不在长度中点**：距 +X 端面 10.2、距 −X 端面 35.0；
- 4 个 M2.5 安装孔在**两个轴向端面**上（方形 9.9×9.9 = 节圆 Φ14），
  原代码却把它们钻在**底板**上（"从底部往上拧"），所以笼子实际上没有跟舵机连上。

### 1.4 附带发现的零件内"飘块"（预览里的碎料）

- `joint_cage`：插接芯棒写成 `z_cap_bot + wall + 2.0`，凭空留了 2 mm 空气缝
  → Φ34 芯棒成为**独立实体**；减重窗高 30 且越过顶板 → 侧板被切成**两块 73 mm³ 碎料**。
  合计 4 个实体（应为 1）。
- `joint_cage_yaw`：角柱高度按 `2*z_sec` 算（假设两端对称），
  修正轴向尺寸链后两端不再对称 → 角柱短 3.5 mm，够不到端板。

### 4.3 已排除的一种"看起来能修"的方案（有实验数据）

**只把舵机绕自身轴转 180°（4 孔阵 4 重对称，不影响拧螺钉）解决不了这组干涉。**
`design/cad/fit_clocking.py` 对 22 个关节逐个试了 `parent` 与 `-parent` 两个钟点：

| 关节 | 翻转前 | 翻转后 | 结论 |
|---|---|---|---|
| `head_pitch` | 3 450 | **2 011** | 有效但没清零 |
| `left_hip_pitch` | 3 978 | 3 913 | 基本无效 |
| `left/right_hip_roll` | 7 521 | 7 521 | **完全无效** |
| `left/right_shoulder_roll` | 16 255 | 16 255 | **完全无效** |
| `right_gripper` | 8 223 | 8 223 | **完全无效** |

原因：这些互咬发生在**沿轴方向**（两个机体在轴向上占据了同一段空间），
绕轴转 180° 不会改变轴向占据 → 必须**把机体沿自身轴向挪开**，
或改框架上的舵机座位置。两者都会动到包络与质量 → 属布局决策。

### 4.4 修正带来的一个副作用（质量变了，做重量方案时用新数）

零件包络按真实舵机尺寸修正后，"把 35 当垂直高度"造成的虚胖消失：

| 项 | 修正前 | 修正后 |
|---|---|---|
| 打印结构件合计 | 1 789 g | **1 404 g**（−22%） |
| 整机合计 | 3 435 g | **3 050 g** |
| 踝关节力矩需求 | 1.68 N·m（114% / 占堵转×50%） | **1.49 N·m（102%）** |
| 整机包络 | 129 × 223 × 418 mm | **129 × 204 × 407 mm** |

> 也就是说：**讨论重量方案时请以 1 404 g 结构 / 3 050 g 整机为基线**，
> 旧表格里的 1 789 / 3 435 是"舵机尺寸用反"时期的虚高值。

## 6. 追加诊断：重叠量级的"性质"与一条硬根因

> 触发：复查时提出质疑——"这些重叠体积完全不合理，这可是零件设计模型而不是包络轮廓"。
> 质疑成立。下面是把它量化后的结论，以及**订正我在第 4.1 节的错误归类**。

### 6.1 判读指标：看**重合率**，不要看绝对体积

`audit_assembly.py` 已升级：每对干涉同时给出
**重合率 = 交集体积 ÷ 较小件自身体积**，并据此分性质：

| 判定 | 阈值 | 含义 | 处置 |
|---|---|---|---|
| ❌ **摆放错误** | 重合率 ≥30% 或 ≥5 000 mm³ | 两个零件被指派到**同一块空间** | 改尺寸**无解**，必须改摆放/基准 |
| ⚠️ 让位不足 | 5–30% 或 500–5 000 mm³ | 局部让位不够 | 改尺寸/倒角/挪位可解 |
| · 局部干涉 | 其余 | 小干涉或假阳性 | 逐条确认 |

修正后的实测（2026-09-11 晚）：

```
性质判定：摆放错误 37 对 ｜ 让位不足 152 对 ｜ 局部干涉 52 对
体积分布：≥10 000 mm³ 11 对 ｜ 5 000–10 000 12 对 ｜ 1 000–5 000 106 对
          ｜ 100–1 000 97 对 ｜ <100 15 对
按零件统计：Raspberry Pi 被侵占 90%、torso_frame 56%、trunk_pitch 舵机 127%、
          battery_tray 147%、electronics_deck 174%（自身体积占比）
```

**"某零件被侵占 > 自身体积"在物理上不可能**——只有当一个零件同时插进好几个邻居时才出现。
这直接说明：**问题不在配合公差，而在摆放层**。

### 6.2 硬根因（已复现）：电子件摆放分支的 key 不匹配，7/7 全部落空

`assembly.py` 里有两张"落座/背挂"表：

```python
ELEC_DECK_TOP = {"compute": 42.0 + 2.6, "battery": 18.0 + 2.6}
ELEC_BACKPACK = {"mcu": 0, "servo_driver": 1, "bec": 2, "amp": 3, "speaker": 4}
```

而 `placements.json` 里的 id 是**长显示名**：`Raspberry Pi 4B (4GB)`、`STM32F405RGT6 核心板`、
`飞特 URT-1 总线驱动板`、`XL4015 降压模块`、`PAM8403 功放模块`、`4Ω 3W 腔体喇叭 Φ28`、
`3S 11.1V 2000mAh 10C 锂聚合物 (XT60)`。

复现：

```bash
.venv-cad/bin/python -c "
import sys, json; sys.path.insert(0,'design/cad'); import assembly as A
pl = json.loads((A.DESIGN/'placements.json').read_text(encoding='utf-8'))
ids=[e['id'] for e in pl['electronics'] if e['link']=='torso_upper']
print('命中托盘分支', [i for i in ids if i in A.ELEC_DECK_TOP])
print('命中背挂分支', [i for i in ids if i in A.ELEC_BACKPACK])"
# → 两个分支都是 0 件（共 7 件）
```

**后果**：7 件电子件全部停在 `placements.json` 的原始局部坐标上
（树莓派 local z=−12、电池 local z=−26），而躯干舵机就占着那一段
→ 树莓派与 `trunk_pitch` 舵机 69% 重合、与电池 25% 重合、与托盘 71% 重合……
**这是静默失效（silent no-op），不是设计冲突。**

> **订正**：本记录第 4.1 节把这一组归为"容积超额，等重量方案定案再摆"——**归类错了**。
> 其中相当一部分是**代码 bug**（分支从未生效），跟重量方案无关，应当**现在就修**。

### 6.3 这一类问题缺的不是"数值"，是"判据与契约"

连续两次踩同一类坑（舵机坐标系、电子件分支），共同点是
**摆放层没有"基准 + 配合 + 断言"**：位置靠手写常数、坐标系隐式转换、
分支 key 靠字符串匹配且失败不报错。

因此需要补齐的能力（分成三类，前两类适合向外要世界知识，第三类是本仓库工程）：

| 类别 | 缺什么 | 怎么补 |
|---|---|---|
| **判据（数值表）** | 界面类别 → 允许重叠/最小间隙 → 判读阈值 → 假阳性清单（贴合面、相切、螺纹、标准件、阵列件） | **向 Gemini 要**：`第4轮-给Gemini的提示词-装配校核方法与堆叠惯例.md` K1/K3 |
| **方法（惯例）** | 基准/配合（datum/mate）建模惯例；DFA 可达性与顺序校核；极限姿态扫掠体积校核；小轴距多舵机堆叠惯例；打印框架座口与减重规则；该结构族失效模式清单 | **向 Gemini 要**：同一份 prompt 的 K2/K4/K5/K6/K7/K8 |
| **工程（本仓库）** | ① 稳定 ID（`placements.json` 的 `id` 只作显示名，另加 `kind`/`ref` 字段做程序索引）；② **分支未命中即失败**的断言；③ 零件"基准声明"（datum）与装配断言；④ 体检进入 CI（阈值：摆放错误=0、关节轴对齐=22/22、每零件单实体） | 我实现（等 K1/K2 的回值确定阈值与字段设计） |

### 6.4 立即可做的两件事（不依赖外部输入）

1. **修 6.2 的静默失效**：给 `placements.json` 的电子件加稳定 `kind` 字段，
   装配层改用 `kind` 索引；命中数为 0 时**直接抛错**而不是静默跳过。
2. **给摆放加断言**：每个零件装配后立刻检查"是否与已放置件发生 ≥5 000 mm³ 的重合"，
   一旦发生就报出零件名并中止——把"摆错"从"事后体检"提前到"装配时立即失败"。
