# 诊断：为什么 `deepseek-v4.1-flash` "感觉只有 200 tok/s"

> 日期：2026-09-12 12:00–12:10｜执行：主会话｜工具：`scripts/llm-throughput-probe.py`（本次新建）

## 一、结论（先看这个）

**200 tok/s 不是 `deepseek-v4.1-flash` 的速度上限——它的实测生成速度是 ~726 tok/s，比你以为的快 3.6 倍。**
你感知到的"慢"来自另外两个环节，而且**都与解码速度无关**：

| 环节 | 实测 | 说明 |
|---|---|---|
| **① 首字节延迟 TTFT** | **中位数 6.70 s**（3 次：6.70 / 6.77 / 6.47） | 每次请求都要先等 ~6.7 秒才有**第一个** token 出来 |
| **② 思考（reasoning）** | 首字思考 = 首字节 = 6.7 s；首个**正文**字要到 **7.96–10.01 s** | 前 1.2–1.5 秒（约 1100–1500 字）全在 reasoning，屏幕上看不到东西 |
| **③ 解码（真正吐字）** | **403 / 726 / 732 tok/s，中位数 726 tok/s** | 这一段快得离谱，v4.1-flash 是台小模型，解码不是瓶颈 |

**所以"200"这个数其实来自另一个模型**：同网关的 `deepseek-v4-flash` 实测生成期中位数 **222 tok/s**（85–386）——
和你的 200 几乎一模一样。**你很可能把 `deepseek-v4-flash` 的观感记到了 `v4.1-flash` 头上**，
或者只是在 DSH 里切模型时看的是同一个会话的残留印象。

## 三、关键判读（怎么区分"模型慢"与"客户端慢"）

探针除速度外还测了两个**指纹**：

1. **chunk 间隔中位数**：v4.1-flash 是 **0.0 ms**（一批 SSE 事件连续到达，网卡一次收一堆），
   而 v4-flash 是 **8–15 ms 的稳定栅格**（服务端按固定节奏推送）。
   **固定栅格 = 服务端节流**；0 ms + 大批量 = 服务端一次给完、只是被网络分片。
2. **每 chunk 平均字符数**：v4.1-flash ≈ **2.0**；v4-flash 有一次高达 **10.5**（说明服务端把 10 个字符合成一个事件推）。
   这解释了为什么 v4-flash 的 token 计数与观感对不上。

**DSH 客户端这一侧不是瓶颈**：我在 DSH 的 60+ 个已安装包里全文检索
`tok/s`、`tokensPerSecond`、`tokens_per_second`、`throughput`，**一个都没有**——
DSH **根本不显示 tok/s**。所以"200 tok/s"不可能是 DSH 报给你的数，它是你的观感估计。
（即便如此，客户端渲染也确有节流设计，但那只会影响**视觉刷新**，不影响实际吞吐。）

## 四、那"慢"到底慢在哪 —— 一笔时间账

以第 3 次（最快的一次）为例：**总时长 8.40 s，其中**

- **6.47 s（77%）** 在等首字节 —— 纯排队/prefill，**屏幕上什么都没有**
- **1.49 s** 在吐 reasoning（约 1167 字，不可见的"思考"）
- **0.44 s** 才轮到正文（246 字）

**你盯屏幕看到的"慢"，77% 是首字节延迟，剩下大半是看不见的 reasoning。**
解码本身只占 5%。

而 `agent-default-model.reasoningEffort = max` —— 每轮都在跑满档思考，
所以"等 6.7 秒 → 一堆隐藏思考 → 正文飞快刷完"就是你观感的全部来源。

## 五、能做什么

| 手段 | 效果 | 代价 |
|---|---|---|
| **降 `reasoningEffort`（max → high/low）** | 直接砍掉大量的思考 token，**观感提升最明显**（省时间的大头在"首正文 7.96–10.01 s"这段） | 复杂任务的推理质量下降；建议只对"执行型"会话降档 |
| **接受 6.7 s TTFT** | 这是网关/模型的固定开销，**客户端无法优化** | — |
| **别用 `deepseek-v4-flash` 干重活** | 它才是真·200 tok/s 那个（还出现过 85 tok/s） | — |
| **`grok-4.6` 只用于短评审** | 首字节 8–88 s，写整模块会等到天荒地老 | — |

> ⚠️ **诚实说明（本机网络前提）**：以上是**经"猫猫云"透明代理**测得的数字。
> 隧道 RTT 约 200 ms，6.7 s 的 TTFT 里有多少是隧道、有多少是网关排队，**本次没有分离**。
> 若要在无代理环境复核，重跑 `scripts/llm-throughput-probe.py` 即可（stdlib，无依赖）。
