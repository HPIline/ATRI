## 0. 赛题原文与起点事实核查

赛题原文（第 3 轮 T6 复取）：

> **「② 二维码循迹：识别二维码并按指示路径行走。」**

开工前先查代码，不读文档：

| 环节 | 事实 | 缺口 |
|---|---|---|
| `atri/qrgen.py` 生成 | 能生成**单条指令**二维码，参数校验完整 | **表达不了"路径"** |
| `atri/perception/opencv.py` `detect_qr` | `cv2.QRCodeDetector().detectAndDecode()` 单次裸调用 | 无鲁棒性处理、无对照数据 |
| `atri/skills/qr.py` 执行 | 单动作分发（walk / turn / dance） | 只能执行一条指令 |
| `atri/cerebellum.py` `walk()` | 生成关节轨迹并下发 | **没有位移/里程计——不记录"走到哪了"** |
| 二维码测试 | 22 项，全是 `qrgen` 参数校验 | **没有一项用真二维码图验证"编码→解码"** |

**两个要害：**

1. 赛题要"按指示**路径**行走"，而 payload 只能表达一条指令 —— 这是本次要补的核心缺口。
2. S-02 判据里的 `path_error_mm_max: 50`（到位误差）**当前无法验证**：
   小脑层没有位移模型，"走对没有"无从谈起。这一点与 T-01 的"没有取帧入口"属同一类问题，
   处理方式也一致：**能测的测实，不能测的明确标为未测**，不拿标称值冒充实测。

## 1. 目标与验收

| 指标（来自 BOM 表） | 目标 | 本次怎么量 |
|---|---|---|

## 2. 数据流

```
摄像头帧
 └─ QrDecoder（三选一：opencv / aruco / wechat）
      └─ payload 字符串
           └─ path_plan.parse_payload   ← 生成端与执行端**共用同一套校验**
                ├─ 新格式 {"schema":"atri.path.v1","path":[...]}
                └─ 旧格式 {"action":"walk","steps":3} → 自动视为单段路径
                     └─ skills/qr.py 逐段执行（任一段失败即停）
                          └─ odometry.NominalOdometry 推演**标称**位移
```

## 3. 路径格式

```json
{
  "schema": "atri.path.v1",
  "path": [
    {"action": "walk", "steps": 3},
    {"action": "turn", "deg": 90},
    {"action": "walk", "steps": 2}
  ]
}
```

**为什么带 `schema`**：赛题**未规定**路径的表达格式（主办方口径待确认，T6 文档的 Q3）。
带版本号的字段让"将来对齐主办方格式"或"同时兼容多种格式"都有落脚点，
而不是等到现场才发现格式对不上。

**为什么保留旧格式**：现场可能已经印好二维码。旧格式被解析为**单段路径**，
`Path.source` 会标明这次走的是 `legacy` 还是 `path`。解析结果序列化回去仍是旧格式，
保证"同一个码，改前改后读出来一样"。

**约束（生成端与执行端同源，实现只有一处）**：

| 项 | 上限 | 出处 |
|---|---|---|
| 单段步数 | 20 | `config.MAX_STEPS`（既有） |
| 单段转角 | ±135° | `config.MAX_TURN_DEG`（既有） |
| 单段舞曲 | 8 小节 | `config.MAX_BARS`（既有） |
| **路径段数** | **16** | 本次新增 `MAX_PATH_SEGMENTS` |
| **路径总步数** | **60** | 本次新增 `MAX_PATH_TOTAL_STEPS` |

> 新增两道闸的理由：单个二维码容量有限（版本 40 / 纠错 L 约 2953 字节），
> 且"现场走一条 16 段以上的路径"本身就不现实；总步数预算防的是"20 段 × 20 步"这种跑不完的指令。

## 4. 三个关键决策（都有实测依据）

### 4.1 解码器：三个都实现，用数据定主用

先做能力探测，再定方案：

| 解码器 | 依赖 | 判据子集成功率 | 全扫描成功率 | 平均单帧 |
|---|---|---|---|---|
| `opencv`（`QRCodeDetector`） | opencv 自带 | 50.0%（3/6） | 66.7% | 105.7 ms |
| `aruco`（`QRCodeDetectorAruco`） | opencv 自带 | 66.7%（4/6） | 59.3% | 54.0 ms |
| **`wechat`（`WeChatQRCode`）** | **4 个模型，共约 1 MB** | **100%（6/6）** | **88.9%** | **25.9 ms** |

**结论：主用 `wechat`。** 它不只是最准，还是**最快**的 —— 标准 `QRCodeDetector` 反而最慢。
两个自带解码器"零下载"的优势，抵不过判据条件下 50% / 66.7% 的成功率。

模型不入库（与 T-01 同一套做法）：`fetch_models.py` 拉取 + sha256 校验。
WeChat 的 4 个文件里有一半是 Git LFS 文件，**本机实测两类文件的可用下载路径不同**，
脚本按顺序试多个来源（见脚本头部注释）。

### 4.2 执行：多段 + 失败即停

三个刻意的语义：

1. **任一段失败就停**，报出"第几段、什么原因"。不跳过继续走 —— 走偏比停在原地更糟。
2. **段间也检查中止信号**。任务级超时若只在单段轨迹内部生效，一条 6 段路径会跑成 6 倍时长。
   为此给 `Cerebellum` 加了公开的 `aborted()`（原先只有私有的 `_aborted()`）。
3. **非法路径在动手之前拦下**：解析阶段就报错，不会"走了一半才发现第 3 段越界"。

### 4.3 位移：建标称模型，但标注为**未标定**

`atri/odometry.py` 按步态参数做几何折算（每步位移 × 步数、转角 × 转向效率），
给路径一个**名义终点**，并给实机标定留好接口（`config/odometry.json`）。

**它是设计值，不是实测。** 输出的每条结果都带：

```json
{"status": "nominal-uncalibrated", "calibrated": false,
 "caveat": "标称值：按步态参数几何折算，未经实物标定，不可当作实测指标"}
```

标定方式（实机阶段）：让机器人直走 N 步、原地转 90°，量出真实位移与角度写进配置文件，
模型自动切到 `calibrated`。

## 5. 实测结果摘要

完整数据见 `design/handoff/T-02-二维码识别鲁棒性报告.md`（27 个场景，三解码器对照）。

| 指标 | 实测 | 目标 | 判定 |
|---|---|---|---|
| 二维码识别成功率（**判据条件子集**：固定光照、≤1 m） | **100%（6/6）** | ≥ 90% | ✅ |
| 二维码识别成功率（**全扫描**，含超出判据的极端扰动） | 88.9%（24/27） | — | — |
| 二维码 JSON 指令执行正确率 | **100%（10/10）** | ≥ 95% | ✅ |

**耐受边界（仍能解出的最严档位）**：

| 扰动 | 边界 |
|---|---|
| 码宽 | wechat 60 px 可解；**45 px（名义 148 cm）三种全失败** —— 这是唯一的硬边界 |
| 旋转 | ±60° 三种都能解（二维码的定位图案起了作用） |
| 透视倾角 | wechat 40° 可解；**55° 三种全失败** |
| 高斯模糊 | wechat 到 k=9 仍可解；aruco 在 k=5 起失败 |
| 亮度 / 噪声 | 三种都扛得住（×0.4 ~ ×1.3、σ 到 30） |

**工程结论**：现场的成败主要取决于**码在画面里占多少像素** ——
要么把卡片印大，要么走近。这条比"换个解码器"重要得多。

## 7. 复现命令

```bash
# 环境（在 .venv-face 里，与 T-01 共用）
.venv-face/bin/pip install "opencv-contrib-python==4.11.0.86" "numpy<2" qrcode

# 拉二维码模型（带 sha256 校验，约 1 MB）
.venv-face/bin/python software/atri/tools/fetch_models.py --only qr

# 生成一张路径二维码（并打印版本/模块数/像素尺寸）
.venv-face/bin/python -m atri.qrgen \
    --path '[{"action":"walk","steps":3},{"action":"turn","deg":90}]' -o qr_path.png

# 跑鲁棒性评测（三解码器对照 + 10 组指令回放）
.venv-face/bin/python software/atri/tools/qr_eval.py \
    --report design/handoff/T-02-二维码识别鲁棒性报告.md

# 单元测试
cd software/atri && python3 -m unittest discover -s tests -p "test_qr*.py"
```
