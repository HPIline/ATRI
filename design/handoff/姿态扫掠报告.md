## 二、`sweep_check.py` 到底哪里坏了（根因）与修了什么

### 缺陷 1（致命）：零位基线**从未用 FK 摆到世界位姿**

`compute_baseline()` 直接把各 link 的碰撞体**在 link 局部坐标系下两两求交**，从头到尾没有乘 `kin0.world[link]`。后果：所有零件被当成"都堆在原点"比较，于是

- 基线虚高且**完全是假象**：实测得到 **163 对 / 6 910 468 mm³**，其中 `pelvis × torso_upper` 339 115、`head × torso_upper` 223 258、`left_foot × torso_upper` 102 312、**`head × left_foot` 88 200 mm³**——脚和头在零位根本不可能相交；
- 同时**漏掉真实基线**：`left_forearm × left_hip_yaw_link` 在零位真相交 7 280 mm³，而基线表里它是 0。

**复现证据（真实输出）**：把名义零位姿态 `{}` 送进原脚本，照样报出 8 个"事件"，其中 `left_forearm × left_hip_yaw_link: 7280 mm³（基线 0）`。零位姿态本该一个事件都没有。

**修法**：基线改为在**零位世界位姿**下求交（零件本来就由 `build_assembly` 摆在零位世界系里），并且每个姿态用
`M_delta(part) = world[link](姿态) · world[link](零位)⁻¹`
对零件做刚体搬运——这样零位时 `M_delta = I`，与权威装配**逐字节等价**。

### 缺陷 2（致命）：排序口径是**绝对体积**，不是"扣基线后的新增"

```python
worst = max(evs, key=lambda e: e.vol - 1.0)          # ← 减的是 1.0，不是基线
"max_excess": max(e.vol - 1.0 for e in evs)          # ← 同上
records.sort(key=lambda r: -r["max_excess"])
```

`CollisionEvent` 里**根本没存过基线**，所以"新增"永远算不出来，榜单一律被零位就存在的大干涉霸占——这正是你提醒的"会把零位本来就有的 189 对当成姿态问题"。

**修法**：`Event` 增加 `base` 字段，`excess = v(姿态) − v(零位)`，一切排序、门限、限位依据全部走 `excess`。

### 缺陷 3（致命）：几何来源是 **URDF `<collision>` 实心包络代理块**，不是零件

原脚本从 `atri.urdf` 读 `<collision>` 盒体当碰撞体。实测这些盒子是**整块实心包络**：

```
torso_upper  vol=612226 mm³  bbox=100x175x127   ← 一个 100×90×55 的实心块 + 3 个舵机块
pelvis       vol=399626 mm³  bbox=100x115x74
left_thigh   vol=201683 mm³  bbox=45x45x89      ← 实心，不是 Φ40 管
left_foot    vol=223258→110x60x19.6 实心块
```

拿它扫掠必然"一动就撞"，而且撞的是包络块互相穿，**和真实零件无关**。

**修法**：改用 `assembly.build_assembly(A.Kin(urdf), placements)` 的 **86 个真实零件**（只读内存、不写盘），并把 `assembly.Kin` 作为正解唯一实现。改用真实零件后零位基线立刻落到**与权威口径逐位一致**（§四）。

### 缺陷 4：零件→link 归属必须按"**fork 随子级转**"，而 `build_assembly` 不是

`assembly.build_assembly()` 把 `fork__J` 放在 `kin.joint_world(J)`（= **父** link 的关节系），这只在零位与"子 link"等价。零位体检全在零位做，所以历史产物没问题；但**姿态扫掠必须按子 link 归属**，否则一弯关节"叉不跟着小腿转"，结果全错。

`preview.py` 第 209–221 行已经把正确口径写死并实现了（"`fork__J` → 子 link（叉锁在舵盘上，跟着子级转）"），`skeleton.limb_fork()` 的 docstring 也说"一侧螺栓锁在金属舵盘上"。

**修法**：本脚本独立实现同口径（`servo/cage/outrigger__J` → 父 link；`fork__J` → 子 link；`elec__id` → `placements.json` 的 host link；`{link}__{part}` → 名称前缀），并用 `--selftest` 与 `preview.part_link()` **逐件对拍 86/86 通过**。

### 缺陷 5（隐性）：`Workplane.val()` 的多实体盲区

`fitcheck.common_volume()` 取 `a.val()`，而 CadQuery 的 `Workplane.val()` **只返回 `objects[0]`**。全机唯一的多实体零件 `torso_upper__torso_frame`（**3 个互不相连实体**）因此有 **21 983 / 130 183 mm³（17%）几何对判定链路不可见**（`interference.py` / `assembly.py` / `audit_assembly.py` 同样受影响）。

**修法**：本脚本把每个零件的**全部实体**包成 `Compound` 再判定（`wrap_all_solids()` / `restack_all_solids()`），并用 `shape0_legacy` 保留旧口径以做对账。量化结果见 §四。

### 缺陷 6（能力缺失，不是 bug）

原脚本没有：`is_joint_mate` 配合面标注、逐关节限位区间、PNG 图、JSON、判定口径分层、预算控制、自检、只重出图。均已补齐。另外 `--quick/--full` 的语义按你给的契约**保持不变**（3 档/50 组、5 档/200 组）。

### 缺陷 7（方法学，本轮新发现并修掉）：1 mm³ 门限会把"零位既有干涉的微小增长"误判成"首撞"，从而给出荒谬限位

修好前 6 项后，用"任意对新增 > 1 mm³"当首撞判据，扫出来的是：

| 关节 | 原判据首撞角 | 命中对 | 该姿态体积 | 零位基线 | 新增 |
|---|---|---|---|---|---|
| `head_yaw` | **+0.93°** | `head_yaw_link__compact_adapter ↔ cage__head_yaw` | 938.5 mm³ | **936.6 mm³** | 1.9 mm³ |
| `head_pitch` | **+0.46°** | `servo__head_pitch ↔ elec__UVC 相机` | 3 661.4 mm³ | **3 556.4 mm³** | 105.0 mm³ |

按这个判据，`head_yaw` 的可用行程会被压到 0.93°，`head_pitch` 压到 0.46°——**机器人等于不能动**，而真正的问题是零位让位不足（相机埋进 head_pitch 舵机、转接块贴住 yaw 笼），**该改几何，不该限位**。

**修法**：把事件分成两类，并只用第一类做限位依据：

- **`new`（真·姿态诱发碰撞）**：零位**不干涉**（基线 ≤ 1 mm³）、该姿态下才相交 > 1 mm³；
- **`worsen`**：零位已经干涉（189 对里那些），该姿态下进一步变大——属零位几何问题，**收紧限位治不了它**，只作信息报告。

首撞角只对 `new` 做二分细化（0.5°），并另给一档 `new10`（> 10 mm³ 的宽松口径）。

## 三、方法与口径

1. **几何**：`assembly.build_assembly()` 的 86 个真实零件（只读内存，不写盘）。
2. **运动学**：`assembly.Kin(urdf, pose_deg)`——正解的**唯一**实现，不另写一套（v1 曾因"预览一套、装配一套"导致每个关节差 90°）。
3. **零件搬运**：`M = world[link](姿态) · world[link](零位)⁻¹`（刚体），零位时为单位阵 ⇒ 与权威装配严格等价。
4. **判定原语**：`fitcheck.common_volume()`（`BRepAlgoAPI_Common` + 体积属性），**未修改 `fitcheck.py`**。
5. **粗筛 + 精确安全剪枝**：先算 AABB 相交体积 `ov`。因为 `ov` 是真实相交体积的**上界**，所以 `ov ≤ base + 1` 时必有 `excess ≤ 1`，可直接跳过——这是**精确安全**剪枝，不是近似（保守性来自 AABB，只会多算不会漏算）。
6. **完备性论证**：**同一 link 上的零件对永不检查**。它们刚性同步、相对位姿恒定，恒不可能成为姿态诱发碰撞——这是恒等式而非近似。单关节扫掠只检查**跨越该关节子树边界**的零件对（`a ∈ subtree(J)` 且 `b ∉ subtree(J)`），同样是精确的：子树内任意两 link 的相对位姿只由子树内的关节决定，而它们在该姿态下全为 0。
7. **配合面标注**：`fitcheck.is_joint_mate(a, b)` **逐字调用**（未改该文件）；另加一列 `same_joint`（同关节号且双方都是关节件）作为补充口径——因为 `is_joint_mate()` 的允许集合只有 `{servo,cage}` / `{servo,fork}` / `{servo,gripper_jaw}`，**不含 `{servo,outrigger}`、`{cage,fork}`、`{outrigger,fork}`**，而运动学上 `cage/outrigger` 在父、`fork` 在子，**恰恰是真正会相对运动的同关节界面**。
8. **首撞角扫描**：单关节沿 −/+ 方向扫到 URDF 限位，角度按 `(k/n)^1.6` **向 0 加密**（均匀取样在 n=12 时首格就有 3.3°（踝）/7.5°（膝），最容易漏掉"一动就撞"的窄带），再二分细化到 0.5°。
9. **限位建议公式**：`建议限位 = |首撞角| − max(2°, 10%·|首撞角|)`，向下取整到 1°。余量覆盖装配公差（±0.2–0.5 mm）、控制超调与仿真-实物差异。
10. **预算**：`--budget`（秒）是**软预算**——到点即停止采样、按已完成部分出报告并写明"未跑完"；SIGALRM 为硬后备（预算 + 180 s）。冷启动（装配 + 基线 + 对账）**不计入**预算，避免"还没开始采样就超时"。

## 五、已实测的姿态诱发碰撞清单（含配合面标注）

> ⚠️ **适用范围**：本节表格来自**已验证的真实样本**，不是全量 `--quick` 排序（全量排序的 JSON 因进程被杀未落盘）。
