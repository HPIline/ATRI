### 1.1 三件要事的实现要点

**(1) 关节滑条——每帧只算 4×4 矩阵**

- 几何**只在机械零位三角化一次**，烘在世界系；每个零件记住自己刚性所属的 link。
  渲染矩阵 `M(link,q) = W_q(link) · W_0(link)⁻¹`（`W_q` = 当前姿态 link 世界位姿，
  `W_0` = 零位世界位姿，其逆在 build 时算好存进缓存）。
- `W_q` 由 **JS 现算**：`W[child] = W[parent] · T(xyz) · R(rpy) · R(axis,θ)`，
  `xyz/rpy/axis/limit` 全部从 `design/atri.urdf` 读出来写进 HTML（**不手写限位**）。
  每帧只做 22 次关节矩阵 + 23 次 link 矩阵 + 87 次零件矩阵，**不碰顶点缓冲**。
- 滑条范围 = URDF 限位取整（例：`left_knee_pitch` 0…90°、`head_yaw` −90…90°），
  拖动事件只写 `ANG[k]` 并 `request()`，重绘由 `requestAnimationFrame` 合并（一帧最多画一次）。
- **舵机机体挂在父 link**（被母端笼/抱架夹住），`fork` 挂子 link；挂错会在弯关节时"舵机飞出笼子"。

**(2) 姿势预设——一处常量表**：`preview.py` 的 `POSE_PRESETS`（单位度），build 时按 URDF
限位夹紧并打印越界告警（当前 5 个预设**无一越界**，没有告警）。

| 预设 | 关键值（度） | 实测手/脚位置（Python FK 旁证） |
|---|---|---|
| 机械零位 | 全 0 | — |
| 展示姿态 | `A.DISPLAY_POSE_DEG`（肩 −40/肘 −55/爪 20/头 8） | 右手 (69.3, ·, 26.2) |
| 招手 | 右肩 pitch −88、右肘 −90、右肩 roll −12、头 yaw −14 | 右手 (47.4, ·, 100.8)（抬到肩高） |
| 踢球 | 右髋 −60、右膝 +62、右踝 −24；左腿 3/3/−3 | 右脚 (52.2, ·, −153.0) 抬起 31 mm，左脚 −184.0 保持着地 |
| 抓取 | 双肩 −62、双肘 −38、双爪 52、头 pitch 22 | 双手 (78.7, ±88.5, 38.6) 前伸 |

**(3) 配合件半透明——调 `fitcheck.is_joint_mate`**：build 时对 87 个零件两两调用
`is_joint_mate`（364 对组合），把命中的零件标上"配合关节名"，写进 HTML；
勾选「配合件半透明（T）」时这些件 alpha=0.5 且不写深度（先画不透明、后画半透明）。
**点关节名**可进入聚焦模式：该关节的配合件 0.92、其余 0.10（看内部结构的 X 光视角）。

### 1.2 几何缓存（省 CPU 的关键）

```bash
.venv-cad/bin/python design/cad/preview.py --all            # 有缓存 → 0.1 s 重出 HTML
.venv-cad/bin/python design/cad/preview.py --all --rebuild  # 强制重建几何（约 87 s）
.venv-cad/bin/python design/cad/preview.py --all --stale-ok # 不校验指纹，只给"只改 HTML/JS"时躲开重 CAD
```

- 缓存 = 每零件 `{名字, link, 类别, vOff/vCount, iOff/iCount, indexed, mate, aabb}` +
  顶点/法线交错 `float32` 与 `uint16` 索引（base64 内嵌，避免 JSON 文本膨胀 ~3 倍）+ 23 个 link 的
  `zero/inv0` 矩阵 + 22 个关节的 `xyz/rpy/axis/lo/hi/effort` + 5 个预设。
- 指纹 = `skeleton.py`/`assembly.py`/`kit.py`/`parts.py`/`standards.py`/`atri.urdf`/`placements.json`
  的 md5 + `GEOM_VERSION` + 容差。**只改 `preview.py` 里的 HTML/JS 不会让缓存失效**
  （这次 HTML/JS 改了 6 轮，几何只建了 1 次就够；实际因改缓存字段重建过几次，见 §5）。
- 索引化 + **逐顶点面积加权法线**：OCC 的 `tessellate()` 是逐面给顶点（不跨面去重），
  所以在同一个面内平均即可——平面法线完全不变（棱边仍硬），圆柱/倒角变平滑。
  实测**顶点法线与相邻面法线最大夹角 7.3°**（= 曲面的正常平滑量，不是跨棱边抹平）。
  顶点数从 3T（464k）降到 158 860，几何从 12.8 MB 降到 4.74 MB。
- **指纹必须在构建开始时取一次**（本轮踩到的坑）：构建要 1 分多钟，期间别的线程可能改
  `skeleton.py`。第 11 轮真实发生过——T1 用 `git stash` 做对照实验又弹回来，导致
  10:05 那次构建"用 A 版几何建、按 B 版指纹记账"，缓存键与内容不符。
  现在 `build_cache()` 开头取 `fp0 = geom_fingerprint(tol)`、以 `fp0` 落账，
  构建结束再比一次，若变了就打 `[WARN] 构建期间几何源文件被改动`。

## 3. 滑条 / 预设 / 半透明**是否生效**——怎么验的

光"能打开"证明不了交互生效，所以做了三层、都可复现：

### 3.1 静态层（不需要浏览器）

`preview.py --check`：体积、外部依赖、UI 片段、预设/滑条数量、配合件数量。

### 3.2 数值层：**JS 的 FK 与 Python `assembly.Kin` 对拍**（最关键的一条）

`--check` 会从生成的 HTML 里抽出 `//<MATHS>`、`//<FK>` 两个代码块，用 **node** 跑，
读 `_fk_ref.json` 里 Python 侧算的参考矩阵（同一个公式
`MLINK = W_q(link)·W_0(link)⁻¹`），逐元素比：

```
cases=6 links=23 maxAbsErr=4.989e-7 mm  @mixed37/left_upper_arm/[14]
```

6 个姿态 = 5 个预设 + 1 个"每个关节都取 `lo+0.37(hi−lo)`"的合成姿态（22 个关节同时打开），
23 个 link × 16 个元素全比，**最大偏差 5×10⁻⁷ mm**（float32 精度极限）。
⇒ 滑条拖动时几何落在哪里，与 CAD 侧 `Kin` 完全一致，不是"看起来差不多"。

## 5. 未做完 / 主动砍掉的（按性价比）

1. **GLB 仍导出机械零位**（旧版是展示姿态）。几何只烘一次零位，想同时给"当前姿态"的 GLB
   就得再跑一次装配（1–2 min CPU）。砍掉的理由：GLB 是给 Blender/VS Code 二次加工用的，
   零位才是它的正确语义；要看姿态用 HTML。**代价是行为变化，主会话若在意可以让我补一个 `--glb-pose`。**
2. **预设没有做碰撞校核**：只做了 FK 旁证（手/脚落点）与目视。踢球/招手这类大姿态是否穿模，
   应该由 T2 的姿态扫掠给结论；本轮**不重复造判定**。建议 T2 出限位表后，把危险区间在滑条上画红。
3. **半透明的 outrigger 补充规则**是我加的第二条判定路径（原因见 §1.1）。最干净的做法是
   把 `outrigger` 加进 `fitcheck.py` 的 kinds 白名单——那是别人的文件，我没动。
4. **没做**：关节轴可视化、姿态包络实时数字（HUD 只显示零位包络 160×268×407）、
   截图按钮、姿态插值动画、触屏手势、几何 LOD/量化压缩。
   砍的理由：都不影响"当场拖关节给评委看"这条主线；其中"姿态包络"要每帧变换 87 个 AABB，
   与"每帧只算矩阵"的省 CPU 目标冲突，值不当。
5. **缓存重建次数**：本轮因为改缓存字段（`floatCount/vertexCount`、`fkOrder`）与 T1 中途
   `git stash` 对照实验，一共重建了 6 次几何（每次 66–87 s）。
   前几次是我的实现失误（字段语义写错一次、后加 `fkOrder` 一次），最后一次是主会话要求的
   "按 T1 新足版重建"。**不是设计需要**：正常使用下"只改 HTML/JS"是 0.1 s 的（§2.1 已复现）。
